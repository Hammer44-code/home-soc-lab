# Detection: LSASS Process Memory Access (Credential Dumping)

## MITRE ATT&CK

- **Tactic:** Credential Access (TA0006)
- **Technique:** T1003 — OS Credential Dumping
- **Sub-technique:** T1003.001 — LSASS Memory

## Severity

**Critical** — Successful LSASS memory dumping yields cleartext passwords, NTLM hashes, Kerberos tickets, and DPAPI master keys for every account that has authenticated to the host since boot. In a real environment a single confirmed hit is treated as a full credential-compromise event for that endpoint, with mandatory rotation of all interactively-used credentials. Detection has to fire *before* the dump file leaves the box.

## Detection Logic

Two complementary searches. The primary one keys off Sysmon's ProcessAccess events (EID 10) — these are emitted the moment a non-privileged process opens a handle to `lsass.exe` with read/inject rights, *before* any dump file is written. The second is a content-aware fallback that catches the `comsvcs.dll MiniDump` living-off-the-land variant by its command line, in case ProcessAccess events are missed (e.g., Sysmon channel ACL still misconfigured, or the operator disabled rule group 10).

### Primary — Sysmon ProcessAccess (EID 10)

```spl
index=endpoint sourcetype="WinEventLog:Microsoft-Windows-Sysmon/Operational" EventCode=10
TargetImage="*\\lsass.exe"
| where NOT SourceImage IN (
    "C:\\Windows\\System32\\wininit.exe",
    "C:\\Windows\\System32\\csrss.exe",
    "C:\\Windows\\System32\\services.exe",
    "C:\\Windows\\System32\\svchost.exe",
    "C:\\Windows\\System32\\MsMpEng.exe",
    "C:\\Program Files\\Windows Defender\\MsMpEng.exe")
| where match(GrantedAccess, "(?i)^0x(1010|1410|1438|143a|1fffff)$")
   OR match(CallTrace, "(?i)(comsvcs\.dll|dbghelp\.dll|dbgcore\.dll|UNKNOWN)")
| table _time host SourceImage SourceProcessId TargetImage GrantedAccess CallTrace
| sort - _time
```

### Secondary — `comsvcs.dll MiniDump` command-line pattern (Sysmon EID 1)

```spl
index=endpoint sourcetype="WinEventLog:Microsoft-Windows-Sysmon/Operational" EventCode=1
Image="*\\rundll32.exe"
| where match(CommandLine, "(?i)comsvcs\.dll[\s,]+MiniDump")
   OR match(CommandLine, "(?i)#\+?\-?24\b")
| table _time host User ParentImage Image CommandLine
| sort - _time
```

### What each piece does

**Primary SPL:**

- `EventCode=10` — Sysmon "Process accessed". Fires when one process opens a handle to another with non-trivial rights. This is the earliest tripwire for credential dumping: it fires on the `OpenProcess()` call, well before any memory is read or any file is written.
- `TargetImage="*\\lsass.exe"` — scopes the search to handles opened against the Local Security Authority Subsystem Service, which holds every credential cached in memory.
- The `NOT SourceImage IN (...)` block excludes the small set of system services that *legitimately* access LSASS every boot — Service Control Manager, the Client/Server Runtime Subsystem, the Session Manager (wininit), generic svchost-hosted services, and Defender's scanning engine. Excluding these is essential — without it the search returns thousands of benign events per host per day and the real detection gets buried.
- `GrantedAccess` is the access mask returned by `OpenProcess()`. The five values listed are the canonical credential-dumping masks: `0x1010` (PROCESS_VM_READ + PROCESS_QUERY_LIMITED_INFORMATION) is the minimum needed to read memory; `0x1410` and `0x1438` add additional info-query rights; `0x143A` is the mask Mimikatz's `sekurlsa::logonpasswords` requests by default; `0x1FFFFF` is PROCESS_ALL_ACCESS, which `comsvcs.dll MiniDump` and most full-process-clone dumpers ask for.
- `CallTrace` is Sysmon's call-stack capture at the moment of the access. `comsvcs.dll` in the stack is the signature of the LOLBAS MiniDump path. `dbghelp.dll` / `dbgcore.dll` indicate any tool using the standard Windows debugging API to write a minidump (procdump, MiniDumpWriteDump-based custom tools). The literal string `UNKNOWN` in CallTrace is itself a red flag — Sysmon writes `UNKNOWN` when the calling module is not backed by a loaded DLL on disk, which is the fingerprint of reflectively-loaded shellcode (Cobalt Strike's `mimikatz` BOF, in-memory Mimikatz via PowerShell reflection).

**Secondary SPL:**

- Targets `rundll32.exe` specifically because every common form of the LOLBAS minidump is invoked as `rundll32.exe C:\Windows\System32\comsvcs.dll MiniDump <pid> <outfile> full`.
- The regex `comsvcs\.dll[\s,]+MiniDump` matches both whitespace and comma-delimited forms (some evasion variants write `comsvcs.dll,MiniDump` to look like a function-export reference).
- The `#\+?\-?24\b` regex catches the ordinal-based variant — `rundll32.exe comsvcs.dll #+-24` — which calls export #-24 of comsvcs.dll, the same MiniDump function, but evades signatures keyed on the string `MiniDump`. Same whitespace-anchored / regex-boundary lesson applied from T1059.001: don't substring-match `MiniDump` because legitimate debug tooling will hit it inside DLL export names.

## Why This Works

LSASS is the single highest-value target on a Windows endpoint, so its memory layout is well-understood by every credential-dumping tool: Mimikatz, ProcDump, NanoDump, comsvcs.dll, Dumpert, RTCore64 driver abuses, Cobalt Strike's built-in dumper, and dozens of others. They all converge on the same primitive: **call `OpenProcess()` against the LSASS PID with read-memory rights, then either copy memory directly or hand the handle to `MiniDumpWriteDump()`**. Sysmon Event ID 10 is positioned precisely at that primitive — it logs every cross-process handle open against an audited target. There is essentially no way to dump LSASS memory from userland without triggering it.

The detection layers two ideas:

1. **The access mask narrows by intent.** The OS exposes ~20 different access-right bits; an attacker who only needs to *list* LSASS will use `PROCESS_QUERY_INFORMATION` (0x1000) — benign. An attacker who wants to *read* memory must include `PROCESS_VM_READ` (0x0010). The five masks listed in the SPL are the ones that *include* VM_READ and are observed in tooling. Filtering on mask reduces noise from the dozens of legitimate processes that query LSASS metadata (taskmgr, perfmon, AV products).
2. **The call trace confirms the technique.** Even an attacker who uses an "unknown" tool will leave fingerprints — either a recognizable DLL in the stack (comsvcs, dbghelp), or the absence of any backing DLL at all (`UNKNOWN`), which itself is anomalous.

The "tripwire on the syscall" approach is more robust than waiting for a `.dmp` file write because (a) some dumpers stream memory over the network without ever hitting disk; (b) `.dmp` extensions can be renamed or split; (c) dump files written to `\\?\` paths or alternate data streams may not trigger filesystem-based detections at all.

## Tuning Notes

Validated end-to-end against Atomic Red Team test `T1003.001-2` on 2026-05-20. Three findings worth recording, in order from "smallest, technical" to "biggest, structural":

| Finding | What we expected | What we observed | Action taken |
|---|---|---|---|
| **`comsvcs.dll` is surgical, not greedy** | `GrantedAccess = 0x1FFFFF` (PROCESS_ALL_ACCESS) — the most common assumption in detection blogs | `GrantedAccess = 0x1410` (PROCESS_QUERY_LIMITED_INFORMATION + PROCESS_QUERY_INFORMATION + PROCESS_VM_READ) — exactly the minimum rights needed to enumerate + read memory | None — `0x1410` was already in the SPL's mask list. Worth knowing for the writeup. |
| **Defender's LSASS ASR rule blocks at `CreateProcess()`** | `Set-MpPreference -DisableRealtimeMonitoring $true` would be enough to allow the test to run | `Invoke-AtomicTest` failed at `$process.Start()` with `"Access is denied"` even with Real-Time Protection off, because **ASR rule `9e6c4e1f-7d60-472f-ba1a-a39ef669e4b2`** ("Block credential stealing from the Windows local security authority subsystem") survives Real-Time toggle. The rule is enforced by a separate Defender component. | Disabled the ASR rule explicitly: `Set-MpPreference -AttackSurfaceReductionRules_Ids 9e6c4e1f-7d60-472f-ba1a-a39ef669e4b2 -AttackSurfaceReductionRules_Actions Disabled`. Also required Tamper Protection off (GUI-only — `Set-MpPreference` silently no-ops if Tamper Protection is on). |
| **The Sysmon config we deployed was a stub** | Our SwiftOnSecurity-based config was logging all the standard Sysmon event IDs | Sysmon was emitting only EIDs 1, 4, 5 (the always-on events). The `setup/sysmon-config.xml` was the documentation stub from Sprint 1; the real upstream config was never deployed. ProcessAccess wasn't being logged at all — and even SwiftOnSecurity's actual config ships ProcessAccess as `<onmatch="include">` with no rules ("log nothing" per Sysmon semantics, by design, because EID 10 volume in production is unmanageable without tuning). | Replaced the stub with the real SwiftOnSecurity config, added one `<TargetImage name="T1003" condition="image">lsass.exe</TargetImage>` include rule under ProcessAccess. The `RuleName: T1003` field on every captured event confirms it came through our rule. |

**Generalizable lesson:** Detection writing is only the last 20% of detection engineering. The other 80% is making sure the telemetry pipeline is actually carrying the data you think it is. We had a complete detection markdown and a tuned SPL before we discovered Sysmon wasn't logging the event class we needed. Always verify the data is in the index before iterating on the SPL.

**Whitespace-anchored regex lesson from T1059.001:** applied here in the secondary SPL — `comsvcs\.dll[\s,]+MiniDump` requires a delimiter between the DLL name and the export name rather than substring-matching `MiniDump` anywhere on the line. This avoids false-positive hits on legitimate debug tooling that references the symbol in an unrelated context.

**Known false-negative class:** an attacker using "BYOVD" (bring-your-own-vulnerable-driver) — e.g., Mimikatz via `mimidrv.sys` — accesses LSASS from kernel mode and may not generate a userland Sysmon EID 10 at all. Flagged as a known gap; addressed at a higher tier (driver-load detection in Sprint 3 / T1547 family) rather than here.

## False Positive Considerations

LSASS access is generated continuously on a healthy Windows host. The primary sources are:

- **Local Security Authority and session management** — `wininit.exe`, `services.exe`, `lsm.exe`, `csrss.exe`. These access LSASS at boot and at every interactive logon. Already excluded in the SPL by image path.
- **Windows Defender (`MsMpEng.exe`)** — periodically scans process memory of high-value processes including LSASS. Already excluded.
- **Generic `svchost.exe`** — many service-hosted Windows components touch LSASS (Group Policy client, Credential Manager, etc.). Excluded; if your environment runs few third-party services, you can tighten this exclusion to specific service names by joining against Sysmon EID 1 to recover the `svchost.exe -k <group>` parent command line.
- **EDR / AV agents** — SentinelOne, CrowdStrike, Defender for Endpoint, Cylance, and similar products legitimately read LSASS memory as part of their own credential-theft protection or post-breach scanning. Their access masks often *do* include `PROCESS_VM_READ`, so they will not be filtered out by the mask check alone. Whitelist by full image path with the install path *and* signing-cert publisher noted in the SPL comment.
- **Taskmgr / Process Explorer (admin run)** — Sysinternals Process Explorer in admin mode and the Windows Task Manager request fairly broad access (`PROCESS_QUERY_INFORMATION | PROCESS_VM_READ`) on every process it enumerates, including LSASS. This is a known noisy source on developer workstations.
- **Endpoint inventory scanners** — Tanium, BigFix, Lansweeper, and similar agents enumerate processes and sometimes inspect LSASS specifically for credential-hygiene reporting.

**Tuning recommendations:**

1. Run the primary SPL across a 7-day baseline on a known-clean host. Group by `SourceImage` and `GrantedAccess`. Anything that recurs daily from the same image path with the same mask is a candidate for exclusion.
2. Never whitelist `SourceImage` *path* without also pinning down its parent or the binary's signer — attackers can drop a malicious binary at a legitimate-looking path. A tighter rule of thumb: whitelist `SourceImage` only in combination with `ParentImage` matching the expected service host.
3. Keep the `UNKNOWN`-in-CallTrace branch tight — that branch should fire rarely in a baselined environment, and when it does, it is almost always worth investigating (reflectively-loaded code accessing LSASS is a strong signal).

## Test Case

Use [Invoke-AtomicRedTeam](https://github.com/redcanaryco/invoke-atomicredteam) on the soc-victim VM. Run the `comsvcs.dll` test specifically — it does not require disabling Defender and is one of the most widely-observed real-world variants.

```powershell
# Run as administrator in PowerShell
Set-ExecutionPolicy Bypass -Scope Process -Force
Import-Module "C:\AtomicRedTeam\invoke-atomicredteam\Invoke-AtomicRedTeam.psd1" -Force
Invoke-AtomicTest T1003.001 -TestNumbers 2 -GetPrereqs
Invoke-AtomicTest T1003.001 -TestNumbers 2
```

Test #2 in the T1003.001 atomic catalog is "Dump LSASS.exe Memory using comsvcs.dll". It runs:

```
rundll32.exe C:\Windows\System32\comsvcs.dll MiniDump <lsass_pid> C:\Windows\Temp\lsass-comsvcs.dmp full
```

This produces (a) one Sysmon EID 10 with `SourceImage=...\rundll32.exe`, `TargetImage=...\lsass.exe`, full-access mask, and `comsvcs.dll` in the CallTrace; (b) one Sysmon EID 11 (FileCreate) for the `.dmp` file in `C:\Windows\Temp\`.

**Cleanup after the test:** delete the dump file. It contains real credential material from the victim VM's memory and should not be left on disk.

```powershell
Remove-Item C:\Windows\Temp\lsass-comsvcs.dmp -Force
```

To validate end-to-end:

1. Note the wall-clock time before running the atomic.
2. Execute the atomic above.
3. In Splunk, run the primary detection SPL with the time picker set to "Last 15 minutes".
4. Confirm one row appears with `SourceImage=...\rundll32.exe`, `TargetImage=...\lsass.exe`, a non-trivial `GrantedAccess` mask, and `comsvcs.dll` visible somewhere in the `CallTrace`.
5. Run the secondary SPL — it should independently catch the command line.
6. Delete the dump file (see cleanup above).

### Analyst notes on this specific event

- **`SourceImage = rundll32.exe`** — by itself unremarkable; `rundll32.exe` is the legitimate Windows utility for invoking exported DLL functions. The signal is in *what* it's invoking, which is visible in the call trace and in the paired Sysmon EID 1 event's `CommandLine`.
- **`GrantedAccess = 0x1410`** — this is more interesting than the typical detection-blog example. Breaking down the bitmask: `0x1000` (`PROCESS_QUERY_LIMITED_INFORMATION`) + `0x0400` (`PROCESS_QUERY_INFORMATION`) + `0x0010` (`PROCESS_VM_READ`). That is the **minimum** set of rights needed to enumerate the target and read its memory — `comsvcs.dll`'s `MiniDump` function is deliberately surgical, asking for exactly what it needs and nothing more. Many writeups online assume `comsvcs` uses `0x1FFFFF` (PROCESS_ALL_ACCESS); that is wrong, and a detection keyed only on the all-access mask would have **missed this event**. The mask alternation in our SPL anticipated this case.
- **`CallTrace` contains `comsvcs.dll+273ff`** — the smoking gun. `comsvcs.dll` (Component Object Model Services) has no legitimate reason to be on the call stack of an `OpenProcess()` against LSASS. The only function in `comsvcs.dll` that does this is `MiniDump` (export ordinal #-24). The numeric offset `+273ff` is the in-DLL offset of the `MiniDump` call site at the time the access was captured — useful for IR forensics when you want to confirm the same `comsvcs.dll` build was used across multiple hosts.
- **`SourceUser = DESKTOP-0DU4BT6\analyst`** and **`TargetUser = NT AUTHORITY\SYSTEM`** — the attacker is a local admin (`analyst`), accessing a SYSTEM-owned process (`lsass.exe`). The privilege boundary crossing is logged; in an environment without UAC bypass or elevation, this is itself suspicious for a non-privileged account.
- **`RuleName: T1003`** — Sysmon emits this field when a rule's `name` attribute matched. Our lab config has `<TargetImage name="T1003" condition="image">lsass.exe</TargetImage>`, and this is the proof it fired. This field is a useful pivot — `index=endpoint RuleName="T1003"` will show every LSASS-access event regardless of other filters, and is the right starting point for hunting beyond this one detection.
- **Paired Sysmon EID 11 (FileCreate)** — the matching dump file `C:\Users\analyst\AppData\Local\Temp\lsass-comsvcs.dmp` (55 MB) was written immediately after this EID 10. Atomic Red Team uses `$env:TEMP` (user profile), not `C:\Windows\Temp`, by default — worth knowing when correlating dump-file artifacts in a real investigation. EID 11 logging requires the FileCreate rule group in the Sysmon config, which is enabled by default in SwiftOnSecurity's baseline.
