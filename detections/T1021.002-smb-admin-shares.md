# Detection: Remote Services — SMB/Windows Admin Shares (smbexec)

> **Status: validated 2026-06-23.** The second **network-side** detection in this lab (after [T1110.003](T1110.003-password-spraying.md)), and the **first to use the Windows System event log** rather than the Security log. A real lateral-movement-to-SYSTEM was run from soc-kali (`192.168.56.30`) against soc-victim (`192.168.56.20`) with [NetExec](https://github.com/Pennyw0rth/NetExec) (`nxc smb ... -x 'whoami' --exec-method smbexec`), using the already-compromised `analyst` credential from the spray detection. The attack returned `nt authority\system` and produced exactly **one `7045` service-installation event** whose binPath is the unmistakable `smbexec` signature. Both SPLs fired end-to-end: the primary isolated the malicious service (`service_name=cAlUxWGVPn`, `Service_Account=LocalSystem`) on its binPath shape alone, and the correlation SPL recovered the attacker source by joining the local `7045` to the Type-3 `4624` network logon (`logon_user=analyst`, `src=192.168.56.30`).

## MITRE ATT&CK

- **Tactic:** Lateral Movement (TA0008)
- **Technique:** T1021 — Remote Services
- **Sub-technique:** T1021.002 — SMB/Windows Admin Shares
- **Mechanism (cross-mapped):** T1569.002 — Service Execution (Execution, TA0002)

`smbexec` (a method shared by Impacket, NetExec/CrackMapExec, and many C2 frameworks) abuses the built-in administrative shares — `ADMIN$`, `C$`, `IPC$` — that every Windows host exposes to members of the local Administrators group. With valid admin credentials, the attacker opens the `IPC$` named pipe, talks to the **Service Control Manager (SVCCTL)**, and **creates a temporary Windows service** whose command line *is* the payload. The service runs as **LocalSystem**, so the executed command runs as `NT AUTHORITY\SYSTEM` — an instant privilege escalation on top of lateral movement. This is the same family of technique as PsExec; the difference is the delivery method (see Tuning Notes).

## Severity

**Critical.** This is not an *attempt* — by the time a `7045` like this exists, code has **already executed as SYSTEM** on the host. There is no "failed" version of this event: the service was created, which means the SCM accepted the request, which means the attacker held valid administrative credentials and used them. Every firing of the primary SPL is a confirmed compromise requiring immediate containment of both the host and the credential that was used.

## Detection Logic

The detectable shape of `smbexec` is a **service whose image path is a command interpreter running a chained shell payload**, not a real executable. Legitimate services point `ImagePath` at a concrete `.exe` (e.g. `C:\Program Files\...\foo.exe`). `smbexec`'s service points at `cmd.exe` (`%COMSPEC%`) and does a write-execute-delete dance: `echo` the command into a randomly-named `.bat` in `%TEMP%`, redirect its output to a file on the `C$` share so the attacker can read it back over SMB, run the bat, then delete it — all chained with `&`.

Both searches key off Windows **System**-log events under `sourcetype=WinEventLog`:

- **EID 7045** — *A service was installed in the system* (System log, source `Service Control Manager`). The core artifact.
- **EID 4624** + `Logon_Type=3` — the network logon carrying the attacker's source IP, for attribution (the `7045` itself has none — see Why This Works).

### Primary — malicious service install (the compromise)

```spl
index=endpoint sourcetype=WinEventLog LogName=System EventCode=7045
| eval cmd=coalesce(service_path, Service_File_Name)
| where match(cmd, "(?i)(%COMSPEC%|cmd(\.exe)?|powershell)")
| where match(cmd, "(?i)(/c |\.bat|&|2\^?>)")
| table _time host service_name Service_Account cmd
| sort - _time
```

### Secondary — source attribution (compromise + who)

```spl
index=endpoint sourcetype=WinEventLog (LogName=System EventCode=7045) OR (EventCode=4624 Logon_Type=3)
| eval cmd=coalesce(service_path, Service_File_Name)
| eval is_smbexec=if(EventCode=7045 AND match(cmd,"(?i)(%COMSPEC%|cmd(\.exe)?|powershell)") AND match(cmd,"(?i)(/c |\.bat|&|2\^?>)"),1,0)
| bin _time span=5m
| stats sum(is_smbexec) as smbexec_services
        values(eval(if(is_smbexec=1,service_name,null()))) as service
        values(eval(if(is_smbexec=1,cmd,null()))) as service_cmdline
        values(eval(if(EventCode=4624,user,null()))) as logon_user
        values(eval(if(EventCode=4624,src,null()))) as src
        by _time host
| where smbexec_services > 0
| table _time host service service_cmdline logon_user src
| sort - _time
```

### What each piece does

**Primary (service install):**

- Scopes to `LogName=System EventCode=7045` — service installations only. This is the first detection in the lab to read the System log; the Security-log equivalent (`4697`) is **not** audited on the victim, and `7045` is the better artifact anyway because it is on by default and needs no audit-policy change.
- `eval cmd=coalesce(service_path, Service_File_Name)` grabs the binPath. `Splunk_TA_windows` exposes it as both the CIM-normalized `service_path` and the raw `Service_File_Name`; `coalesce` makes the SPL portable to a non-TA index.
- **Condition 1** — `match(cmd, "...%COMSPEC%|cmd(\.exe)?|powershell...")`: the service launches a **shell**. A real service almost never does.
- **Condition 2** — `match(cmd, "...|/c |\.bat|&|2\^?>...")`: the path contains **shell metacharacters** — a `/c` interpreter flag, a `.bat`, command chaining (`&`), or output redirection (`2^>`/`2>`). The carets (`^>`, `2^>^&1`) appear because smbexec `echo`s those characters *literally* into the bat file, so they survive verbatim in the binPath.
- **The two conditions together are the discriminator.** Either alone has occasional benign matches; a service that is *both* a shell invocation *and* full of redirection/chaining is the smbexec/psexec-style pattern and essentially never legitimate.

**Secondary (attribution):**

- Pulls in `4624 Logon_Type=3` alongside `7045`, flags the malicious service with `is_smbexec`, and buckets by `_time` (5-min) + `host`.
- The conditional `values()` aggregations stitch the **local** service-install event to the **network** logon in the same window, recovering `logon_user` (the credential used) and `src` (the attacker IP) — the two facts the `7045` alone cannot provide.
- This is the same correlation idiom as the [T1110.003](T1110.003-password-spraying.md) success-correlation SPL, repurposed to join across two different log channels (System + Security).

## Why This Works

To run code on a remote Windows host through SMB, the attacker must go through the Service Control Manager, and **every service creation is logged as `7045`** — there is no quieter path for this method. The very mechanism that grants SYSTEM (creating a LocalSystem service) is the mechanism that generates the evidence.

The signature is robust because it keys on an **architectural constraint, not a string artifact.** The random service name (`cAlUxWGVPn`) and random bat name (`WImZsu.bat`) change every run — keying on them would be useless. But *every* smbexec variant, across tools, must point the service at a command interpreter and chain a capture-output-then-cleanup sequence, because that is the only way to get command output back over a service-creation primitive that has no stdout. The shape is invariant even though the specifics are randomized.

The attribution gap is itself instructive: `7045` is a **local** SCM event and carries **no source network address** — it cannot, because the SCM doesn't know the request arrived over SMB. The attacker IP lives only in the **Type-3 `4624`** that authenticated the SMB session (confirmed in [T1110.003](T1110.003-password-spraying.md) to carry `src` on network logons). Correlating the two channels is what turns "this host was popped" into "this host was popped by `analyst` from `192.168.56.30`."

## Tuning Notes

Validated end-to-end on 2026-06-23. Run from soc-kali against soc-victim using the `analyst` credential compromised in the spray detection:

```bash
# enumerate the admin shares (confirms Pwn3d! / admin access)
nxc smb 192.168.56.20 -u analyst -p Sledge44 --shares
# execute as SYSTEM via the service-creation method
nxc smb 192.168.56.20 -u analyst -p Sledge44 -x 'whoami' --exec-method smbexec
```

The `--shares` run reported `ADMIN$`/`C$` as `READ,WRITE` and `(Pwn3d!)`; the `smbexec` run returned `nt authority\system`. The primary SPL returned one row (`cAlUxWGVPn`, `LocalSystem`, the full binPath); the secondary recovered `logon_user=analyst`, `src=192.168.56.30`. Calibration findings, all from live data:

**`7045` lives in the System log — and the System log *is* being forwarded.** This was an open question: every prior detection used the Security log only, so it was unknown whether `WinEventLog:System` reached the indexer. The pre-flight `index=endpoint EventCode=7045 | stats count by LogName sourcetype` returned `System / WinEventLog / 1`, confirming System-channel collection. `4697` (the Security-log service-install event) returned **zero** — "Audit Security System Extension" is not enabled — so this detection deliberately uses `7045`, which requires no audit-policy change.

**The `7045` has no source IP (by design).** It is a local SCM event. Source attribution requires the secondary correlation to the Type-3 `4624`. Do not expect `src` on the `7045` itself.

**The service runs as `LocalSystem`** — this is *why* `whoami` returned `nt authority\system`, and `Service_Account=LocalSystem` is a useful corroborating field. It is **not** a good primary filter on its own (plenty of legitimate services run as LocalSystem); the binPath shape is the discriminator.

**Companion events `7000`/`7009` (service failed to start).** smbexec's "service" is not a real service binary, so the SCM often logs a start-timeout (`7009`) or start-failure (`7000`) right after the `7045`. These were not required for this detection but are a strong corroborating signal — a service that is *installed and immediately fails to start* with a cmd-shell binPath is doubly suspicious. A future enrichment could surface them.

**Random service/file names are a secondary signal.** `cAlUxWGVPn` and `WImZsu.bat` are high-entropy, no-dictionary-word strings. The detection does not rely on this (the binPath shape is enough), but an entropy/consonant-run check on `service_name` is a reasonable additional condition for hardening against a variant that uses a less obvious binPath.

**Method coverage — this catches `smbexec`, not every exec method.** NetExec/Impacket offer several remote-exec methods, and they leave *different* artifacts:

| Method | Artifact | Detection |
|--------|----------|-----------|
| `smbexec` | `7045` service install, cmd binPath (**this detection**) | T1021.002 (here) |
| `psexec` | `7045` service install pointing at an uploaded `.exe` in `ADMIN$` (PSEXESVC-style) | partially here; broaden binPath to `\\...\ADMIN$\*.exe` |
| `wmiexec` | no service — `WmiPrvSE.exe` spawns the child process | [T1059.001](T1059.001-powershell-encoded.md) (WMI parent note) |
| `atexec` | scheduled task (`4698`) | [T1053.005](T1053.005-scheduled-task.md) |

So the four exec methods fan out across four detections — a nice illustration that "remote code execution over SMB" is not one signature but a family.

## False Positive Considerations

Legitimate services with a command-interpreter binPath are rare but not unheard of:

- **Software installers / updaters** occasionally register a short-lived service that wraps a script. These usually point at a vendor `.exe` or a named `.cmd` in a Program Files path — not a random `%TEMP%\<rand>.bat` with `C$`-share redirection. The two-condition logic filters most; a vendor allowlist on `service_name`/path handles the rest.
- **Legitimate PsExec use by admins** (Sysinternals) creates a `PSEXESVC` service pointing at a real uploaded binary — it will *not* match this SPL (no shell binPath), which is correct: benign PsExec shouldn't page. If you *want* to flag all PsExec, that's a separate, broader rule.
- **Management/EDR agents** that run remote commands via a service wrapper. Allowlist the known agent's service-name pattern, but log-and-review rather than blanket-suppress.

**Tuning recommendations:**

1. **Page on the primary; the secondary tells you who.** A matching `7045` is a confirmed SYSTEM-level exec — treat every hit as an incident, not an alert to triage later.
2. **Allowlist by binPath/service-name pattern, never by suppressing `7045` wholesale** — losing service-install visibility is a large blind spot.
3. **Add `7000`/`7009` correlation** to raise confidence (installed-then-failed-to-start + cmd binPath ≈ certain smbexec).
4. **Broaden Condition 2 for psexec coverage** by also matching `\\.*\\ADMIN\$\\.*\.exe` if you want service-binary-upload detection in the same rule.
5. **Chain tactics.** This `analyst` credential was compromised by the [T1110.003](T1110.003-password-spraying.md) spray; a spray success followed minutes later by an smbexec from the *same* `src` is an end-to-end intrusion (initial access → lateral movement → SYSTEM). A correlation search across the two is a planned project extension.

## Test Case

Generated from the **soc-kali** attacker VM (`192.168.56.30`) against **soc-victim** (`192.168.56.20`) over the host-only network — no Atomic Red Team, because remote service execution is inherently a network-origin attack.

**Prerequisites:**

- A valid **local administrator** credential on the victim (here `analyst:Sledge44`, compromised in [T1110.003](T1110.003-password-spraying.md)). `--shares` showing `(Pwn3d!)` and `ADMIN$ READ,WRITE` confirms it.
- soc-victim powered on, SMB (445) reachable: `nc -zv 192.168.56.20 445` → `open`.
- NetExec on Kali (`nxc smb --version`).
- No special audit policy needed — `7045` is logged by default. (Optional: enable "Audit Security System Extension" to also get `4697` in the Security log.)

**Run the attack:**

```bash
# On soc-kali
nxc smb 192.168.56.20 -u analyst -p Sledge44 --shares
nxc smb 192.168.56.20 -u analyst -p Sledge44 -x 'whoami' --exec-method smbexec
```

The `smbexec` run returns `nt authority\system`.

**To validate end-to-end:**

1. Confirm `(Pwn3d!)` and `nt authority\system` in the NetExec output; note the wall-clock time.
2. **Pre-flight count** (Last 15 min): `index=endpoint EventCode=7045 | stats count by LogName sourcetype` — confirm a `7045` under `System / WinEventLog` before iterating SPL.
3. Run the **primary** SPL — confirm one row: a random `service_name`, `Service_Account=LocalSystem`, and a `cmd` binPath containing `%COMSPEC%` + `.bat` + `C$` redirection.
4. Run the **secondary** SPL — confirm `logon_user=analyst` and `src=192.168.56.30` aligned with the malicious service.

> **Note on freezes during testing.** smbexec briefly spikes host load (it creates, starts, and deletes a service in one shot). On a RAM-constrained host running all three VMs, this can cause a momentary swap-thrash freeze. Power off the attacker VM once the events are confirmed in the index — the telemetry is already captured and does not require Kali to remain running for the analysis phase.

### Analyst notes on these real captured events

- **`Service File Name` is the entire detection.** A service whose image is `%COMSPEC%` (cmd.exe) running an `echo ... ^> C$\... 2^>^&1 > %TEMP%\*.bat & ... & del` chain is the smbexec fingerprint. No legitimate service has this shape.
- **The carets (`^>`, `2^>^&1`) are literal.** smbexec `echo`s the redirection operators *into* the bat file rather than executing them inline, so they appear escaped in the binPath. Matching `2\^?>` covers both the escaped (`2^>`) and bare (`2>`) forms.
- **`Service Account: LocalSystem`** is why the command ran as `NT AUTHORITY\SYSTEM` — lateral movement and privilege escalation in a single primitive.
- **Random `Service Name` / bat name** (`cAlUxWGVPn`, `WImZsu.bat`) change every run; never key a rule on them. The invariant is the binPath *structure*.
- **`7045` carries no source IP** — `src` came only from the correlated Type-3 `4624`. The `7045` says *what happened on the host*; the `4624` says *who did it and from where*.
- **First lab use of the System log.** All prior detections read the Security log; this confirmed `WinEventLog:System` is collected and opens up the whole SCM/driver/service event family for future detections.
