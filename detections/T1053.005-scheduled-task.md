# Detection: Scheduled Task Creation

## MITRE ATT&CK

- **Tactic:** Persistence (TA0003) / Privilege Escalation (TA0004) / Execution (TA0002)
- **Technique:** T1053 — Scheduled Task/Job
- **Sub-technique:** T1053.005 — Scheduled Task

This single sub-technique maps to three tactics because scheduled tasks serve all three purposes for attackers: they survive reboots (Persistence), can be configured to run as SYSTEM (Privilege Escalation), and execute arbitrary payloads on a trigger the attacker controls (Execution).

## Severity

**Medium-High** — Scheduled tasks are the canonical Windows persistence mechanism: nearly every commodity malware family, post-exploitation framework, and APT toolkit uses them. They are also legitimately used by countless installers and management tools, so the detection cannot be "alert on every task creation" — it has to surface the unusual ones. Per-task triage is the model: every creation is logged, and the analyst looks at task name, run-as user, and the target binary to decide.

## Detection Logic

Two complementary searches. The primary one keys off Sysmon EID 1 invocations of `schtasks.exe` with the `/Create` flag — captures the command-line variant directly. The secondary is a fallback on the Security log's EID 4698 ("A scheduled task was created") which is the canonical event but requires the `Splunk_TA_windows` add-on (or `rex` extraction) for clean field access.

### Primary — Sysmon EID 1 on `schtasks.exe /Create`

```spl
index=endpoint sourcetype="WinEventLog:Microsoft-Windows-Sysmon/Operational" EventCode=1
Image="*\\schtasks.exe"
| where match(CommandLine, "(?i)\s/(create|cr)\s")
| rex field=CommandLine "(?i)/TN\s+\"?(?<task_name>[^\"\s]+)"
| rex field=CommandLine "(?i)/TR\s+\"(?<task_run_q>[^\"]+)\""
| rex field=CommandLine "(?i)/TR\s+(?<task_run_u>[^\"\s]\S*)"
| eval task_run=coalesce(task_run_q, task_run_u)
| rex field=CommandLine "(?i)/RU\s+\"?(?<task_run_as>[^\"\s]+)"
| rex field=CommandLine "(?i)/SC\s+(?<task_schedule>\S+)"
| eval suspicious_run_as=if(match(task_run_as, "(?i)^(SYSTEM|S-1-5-18|NT AUTHORITY\\\\SYSTEM)$"), "yes", "no")
| eval suspicious_target=if(match(task_run, "(?i)(powershell|cmd\.exe|rundll32|regsvr32|mshta|wscript|cscript|bitsadmin|certutil)"), "yes", "no")
| table _time host User ParentImage Image task_name task_run task_run_as task_schedule suspicious_run_as suspicious_target CommandLine
| sort - _time
```

### Secondary — Security EID 4698 (canonical creation event)

```spl
index=endpoint sourcetype="WinEventLog:Security" EventCode=4698
| rex field=_raw "(?ms)Subject:.*?Account Name:\s+(?<subject_user>\S+).*?Account Domain:\s+(?<subject_domain>\S+)"
| rex field=_raw "(?ms)Task Name:\s+(?<task_name>\S+)"
| rex field=_raw "(?ms)Task Content:\s+(?<task_content_xml>.*?)(?=\n[A-Z]|\Z)"
| rex field=task_content_xml "(?s)<Command>(?<task_cmd>[^<]+)</Command>"
| rex field=task_content_xml "(?s)<Arguments>(?<task_args>[^<]+)</Arguments>"
| rex field=task_content_xml "(?s)<UserId>(?<task_user_id>[^<]+)</UserId>"
| table _time host subject_user subject_domain task_name task_cmd task_args task_user_id
| sort - _time
```

### Bonus pivot — Sysmon EID 11 on Tasks folder writes

The XML task definition lands on disk at `C:\Windows\System32\Tasks\<TaskName>` (or `C:\Windows\Tasks\` for legacy at-style tasks). Useful for correlation and for retrieving the full task XML during IR even if the creation event itself was missed:

```spl
index=endpoint sourcetype="WinEventLog:Microsoft-Windows-Sysmon/Operational" EventCode=11
(TargetFilename="*\\Windows\\System32\\Tasks\\*" OR TargetFilename="*\\Windows\\Tasks\\*")
| table _time host Image TargetFilename
| sort - _time
```

### What each piece does

**Primary SPL:**

- `Image="*\\schtasks.exe"` — scopes to the standard scheduled-task CLI. PowerShell's `New-ScheduledTask` / `Register-ScheduledTask` cmdlets and WMI-based variants (`Win32_ScheduledJob`) won't fire here; they're covered by EID 4698, by separate PowerShell logging, or by WMI-specific detections in Sprint 3.
- The `match()` regex `\s/(create|cr)\s` catches both the full `/Create` flag and the documented `/Cr` short form. Whitespace anchors on both sides ensure it's a standalone CLI argument — the same anchored-regex lesson applied in T1059.001 (avoids false matches against parameter values that contain the literal string `Create`).
- The `rex` extractions parse the standard schtasks arguments: `/TN` (task name), `/TR` (task run target), `/RU` (run-as user), `/SC` (schedule type). `/TR` uses two passes — one for the quoted form (`/TR "..."`), one for unquoted (`/TR \S+`) — joined with `coalesce()`. A single alternation regex would be cleaner, but Splunk's PCRE2 rejects duplicate named groups (`PCRE2_DUPNAMES not set`), so two passes is the canonical workaround. See Tuning Notes for the bug this fix replaces.
- `suspicious_run_as` flags tasks created with SYSTEM run-as. A non-privileged user creating a task that runs as SYSTEM is the standard pattern for scheduled-task-based privilege escalation.
- `suspicious_target` flags tasks whose target binary is one of the common LOLBins. A scheduled task pointing at `powershell.exe`, `rundll32.exe`, `regsvr32.exe`, `mshta.exe`, or one of the script hosts is rarely benign in a desktop environment — these are the exact shapes used by malware persistence.

**Secondary SPL:**

- EID 4698 is the canonical scheduled-task creation audit event. It is preferred over the Sysmon-based detection because (a) it fires regardless of *how* the task was created (schtasks.exe, PowerShell, WMI, COM directly), and (b) it includes the full task XML in the `Task Content` field, which the Sysmon command-line view doesn't.
- The `rex` extractions are needed because `Splunk_TA_windows` is not installed in this lab (it's the documented prerequisite for clean 4698 field extraction). The regex pulls the subject user, task name, embedded XML, and from inside the XML the task's `<Command>`, `<Arguments>`, and `<UserId>` (the run-as principal).
- **Note:** EID 4698 requires "Audit Object Access → Other Object Access Events" subcategory to be set to Success in the Local Security Policy. Default Windows 10 settings have this off. The detection markdown's Test Case section verifies whether it's on; if not, the primary SPL covers the validation for now.

## Why This Works

Persistence via scheduled tasks is one of the oldest and most reliable Windows attack patterns. It works because:

1. **The OS gives the attacker survival across reboots for free** — no need to drop a DLL into a startup folder, edit a registry Run key, or maintain a service. One `schtasks /Create` and the payload comes back automatically.
2. **It can be configured to run as SYSTEM** — `/RU SYSTEM` (when executed by an admin) gives the task LocalSystem privileges, which is full host control. This is one of the documented privilege-escalation paths on every red-team checklist.
3. **The trigger is flexible** — at logon, at idle, on a specific time, on an event, every N minutes. Attackers can pick triggers that minimize the chance of being seen by a watchful user.

From a defender's perspective, the technique has one structural weakness: **task creation always touches one of three observable surfaces** — the `schtasks.exe` process invocation (Sysmon EID 1), the Security audit log (EID 4698), or the on-disk XML file in `C:\Windows\System32\Tasks\` (Sysmon EID 11). Any tooling that creates a scheduled task — including legitimate installers, PowerShell cmdlets, and WMI calls — has to hit at least one of these. Combining all three at search time gives near-complete coverage.

The detection here is a "low-friction tripwire" pattern: it surfaces every task creation, decorates the events with risk-indicator fields (`suspicious_run_as`, `suspicious_target`), and lets the analyst sort by those fields to triage the noisy ones first.

## Tuning Notes

Validated end-to-end on 2026-06-02 against Atomic Red Team test `T1053.005-1` ("Scheduled Task Startup Script"). The test creates two tasks in a single run: `T1053_005_OnLogon` (runs as the creating user) and `T1053_005_OnStartup` (runs as SYSTEM via `/RU system`). Both use `cmd.exe /c calc.exe` as the payload. Both fired the primary, secondary, and EID 11 pivot SPLs cleanly. Iteration loops below.

**Iteration loop — `/TR` extraction bug (the lesson from this detection).** The first-iteration regex `(?i)/TR\s+\"?(?<task_run>[^\"]+?)\"?(?=\s/|$)` truncated the captured value to `cmd.exe`, dropping the ` /c calc.exe` portion. The non-greedy `+?` combined with the `(?=\s/|$)` lookahead stops at the *first* space-slash sequence — which inside the quoted value `"cmd.exe /c calc.exe"` is the space before `/c`. The regex didn't respect the quote as a "safe zone." Same class of bug as the substring-wildcard issue caught in T1059.001 — flag/argument-shape ambiguity is sneaky.

**Fix:** two-pass extraction with `coalesce()`. The first pass matches the quoted form (`/TR "..."` → `task_run_q`), the second matches the unquoted form (`/TR \S+` → `task_run_u`), and `coalesce(task_run_q, task_run_u)` returns whichever fired. The natural one-regex solution `(?:"(?<task_run>[^"]+)"|(?<task_run>\S+))` is rejected by Splunk's PCRE2 with `two named subpatterns have the same name (PCRE2_DUPNAMES not set)`. Two passes is the canonical workaround in `rex`.

**Field name confirmation.** Sysmon EID 1 PascalCase auto-extraction confirmed: `Image`, `CommandLine`, `User`, `ParentImage`, `ParentCommandLine`, `Hashes`, `IntegrityLevel`, `CurrentDirectory`. Custom `rex` outputs use lowercase snake_case per Splunk analyst convention. Case-insensitive `(?i)` anchors in the SPL handled the lowercase `/create`, `/tn`, `/sc`, `/ru`, `/tr` flags ART produces — markdown originally predicted PascalCase, both shapes work.

**EID 4698 validation.** Required enabling `auditpol /set /subcategory:"Other Object Access Events" /success:enable` first — off by default on Win10. Two stale events from a hung pre-test invocation that ran *before* the auditpol enable did **not** produce 4698; the two from the clean post-enable run did. Confirms audit policy must be live at task-creation time, not retroactively. The 4698 view is richer than the Sysmon path: `subject_user` (creator) and `task_user_id` (run-as principal) are separate fields in one event, and the run-as appears as a clean SID (`S-1-5-18` for SYSTEM) rather than the literal CLI string `system`.

**EID 11 writer is `svchost.exe`, not `schtasks.exe`.** The Task Scheduler service (`schedule` hosted in `svchost.exe`) persists the XML to `C:\Windows\System32\Tasks\<TaskName>` after `schtasks.exe` hands off via RPC. A naive detection that anchors on `Image=*\\schtasks.exe` for the file-write event would produce zero results — the right anchor for the EID 11 pivot is the Tasks-folder `TargetFilename` regardless of `Image`.

**Whitespace anchoring on `/Create` works as intended.** The regex `(?i)\s/(create|cr)\s` matched the lowercase `/create` form ART uses. Tested mentally against the substring-FP class (a task name like `"Created by IT"` would no longer trip the detection) — the word-boundary anchors hold.

**Anticipated FP categories** (to characterize during a longer baseline — not seen in the lab run):
  - **Windows installers (`msiexec.exe` parent)** — many installer packages create maintenance tasks. Common during patch Tuesday.
  - **Software updaters** — Chrome (`GoogleUpdate.exe`), Adobe (`AdobeARMservice.exe`), Edge (`MicrosoftEdgeUpdate.exe`) install and renew their own scheduled tasks.
  - **Windows Defender itself** — creates several maintenance tasks under `\Microsoft\Windows\Windows Defender\`.
  - **SCCM/Intune deployment** (`ccmexec.exe` parent) — pushes scheduled tasks as part of software distribution.
  - **System utilities run interactively by admins** — manual schtasks invocations during legitimate troubleshooting.

**Known false-negative class:** an attacker using PowerShell's `Register-ScheduledTask` cmdlet or the `Schedule.Service` COM object directly will bypass the primary SPL (no `schtasks.exe` process). EID 4698 covers these — that's why the secondary SPL exists and why the audit policy enable matters operationally, not just for testing.

## False Positive Considerations

Legitimate scheduled-task creation is high-volume on a managed Windows endpoint. Sources to expect:

- **Software installers** during install and uninstall. Both MSI and EXE installers commonly register maintenance, telemetry, or update-check tasks. Pattern: `ParentImage` is `msiexec.exe`, `setup.exe`, or a vendor installer; `task_name` is under a vendor namespace (e.g., `\Microsoft\Office\OfficeBackgroundTaskHandlerLogon`).
- **Auto-updaters** as a steady background. Chrome's GoogleUpdate, Adobe's AdobeARM, Microsoft Edge's MicrosoftEdgeUpdate, and similar all re-register their tasks periodically.
- **Microsoft's own scheduled tasks** — Windows installs ~150 tasks under `\Microsoft\Windows\` by default and refreshes some on updates. The schtasks creation events for these will typically have `ParentImage=*\\TrustedInstaller.exe` or `*\\svchost.exe` and a Microsoft-namespaced task name.
- **Enterprise management agents** — SCCM (`ccmexec.exe`), Intune Management Extension, BigFix, Tanium, Munki, JAMF (for hybrid environments) — all push scheduled tasks for software deployment, inventory, or compliance scanning.
- **Backup software** — Veeam, Acronis, Macrium, and similar register tasks for scheduled backups.

**Tuning recommendations:**

1. **Don't try to whitelist all legitimate sources up front.** Run the primary SPL across a 7-day baseline. Group by `ParentImage` and the namespace of `task_name`. Recurring legitimate creators surface quickly.
2. **Tighten by `suspicious_run_as` + `suspicious_target` first.** Tasks created with SYSTEM run-as AND a LOLBin target are very rarely legitimate outside of Microsoft itself. Sorting the search by those two fields gives an instant priority queue.
3. **Whitelist by `Hashes` (when present)** rather than by image path. An attacker who drops a malicious file at `C:\Windows\System32\schtasks.exe` is unlikely but the right precedent — the hash should match the Microsoft-signed binary. Mismatch = investigate.
4. **For the secondary SPL**, the `task_user_id` field in the XML is the run-as principal. `S-1-5-18` is SYSTEM. Anything other than the task creator's SID, an explicit user account, or a documented service account warrants review.

## Test Case

Use [Invoke-AtomicRedTeam](https://github.com/redcanaryco/invoke-atomicredteam) on the soc-victim VM. The simplest variant is `T1053.005-1` ("Scheduled Task Startup Script") which creates a local task via `schtasks.exe` pointing at a benign command.

```powershell
# Run as administrator in PowerShell
Set-ExecutionPolicy Bypass -Scope Process -Force
Import-Module "C:\AtomicRedTeam\invoke-atomicredteam\Invoke-AtomicRedTeam.psd1" -Force

# Check which atomics are available for T1053.005
Invoke-AtomicTest T1053.005 -ShowDetailsBrief

# Run the local-task variant (test #1)
Invoke-AtomicTest T1053.005 -TestNumbers 1 -GetPrereqs
Invoke-AtomicTest T1053.005 -TestNumbers 1

# Cleanup (removes the task)
Invoke-AtomicTest T1053.005 -TestNumbers 1 -Cleanup
```

Test #1 in the T1053.005 catalog actually creates **two** tasks via chained `schtasks` invocations spawned from `cmd.exe /c ...`:

```
schtasks /create /tn "T1053_005_OnLogon" /sc onlogon /tr "cmd.exe /c calc.exe"
schtasks /create /tn "T1053_005_OnStartup" /sc onstart /ru system /tr "cmd.exe /c calc.exe"
```

The first runs as the current user on logon; the second runs as SYSTEM on startup — one test exercises both the baseline detection and the `suspicious_run_as=yes` flag.

This produces:
- Two Sysmon EID 1 events with `Image=...\schtasks.exe` and `CommandLine` containing the full invocations.
- Two Sysmon EID 11 events with `Image=...\svchost.exe` (the Task Scheduler service writes the XML, not `schtasks.exe`) writing `C:\Windows\System32\Tasks\T1053_005_OnLogon` and `...\T1053_005_OnStartup`.
- Two Security EID 4698 events — but only if "Audit Other Object Access Events" is enabled (off by default on Win10; required, see the auditpol step below).

**Before running**, check whether EID 4698 will fire so we know which SPL path to validate:

```powershell
auditpol /get /subcategory:"Other Object Access Events"
```

If the output shows `Success` is set, EID 4698 will fire. If not, run:

```powershell
auditpol /set /subcategory:"Other Object Access Events" /success:enable
```

(Optional — the primary SPL works regardless. EID 4698 is a nice-to-have for validating the secondary SPL.)

To validate end-to-end:

1. Note the wall-clock time before running the atomic.
2. Execute the atomic above.
3. In Splunk, run the primary detection SPL with the time picker set to "Last 15 minutes".
4. Confirm **two rows** appear: one with `task_name=T1053_005_OnLogon`, `task_run=cmd.exe /c calc.exe`, `suspicious_target=yes`, `suspicious_run_as=no`; one with `task_name=T1053_005_OnStartup`, `task_run_as=system`, `suspicious_run_as=yes`, `suspicious_target=yes`.
5. (If audit logging is on) Run the secondary SPL and confirm two corresponding EID 4698 events. The OnStartup row's `task_user_id` will be the SYSTEM SID `S-1-5-18`; the OnLogon row's `task_user_id` will be the creator's SAM name.
6. (Bonus) Run the EID 11 pivot and confirm both task XML files were written by `svchost.exe` to `C:\Windows\System32\Tasks\`.
7. Run the atomic cleanup to remove both tasks.

### Analyst notes on this real captured event

- **`Image = C:\Windows\System32\schtasks.exe`** — the canonical scheduled-task CLI. Microsoft-signed (`Company: Microsoft Corporation`), lives in `System32`, current Win10 22H2 build (`FileVersion: 10.0.19041.5965`). The `SHA256` (`2327E073...`) is the legitimate signed binary. A renamed or repackaged copy at any other path — or a hash mismatch on something that *claims* to be `schtasks.exe` — is itself a triage signal worth chasing.
- **`CommandLine: schtasks  /create /tn "T1053_005_OnStartup" /sc onstart /ru system /tr "cmd.exe /c calc.exe"`** — the standard `/Create /TN /SC /RU /TR` pattern, all lowercase. The `(?i)` anchors in the SPL handle the case. Note the **double space** between `schtasks` and `/create` — an artifact of how Invoke-AtomicTest constructs the string; harmless because `\s` in the anchor regex matches any whitespace count.
- **`ParentImage = C:\Windows\System32\cmd.exe`** with **`ParentCommandLine`** containing **both** chained `schtasks /create` invocations joined by `&` — `"cmd.exe" /c schtasks /create /tn "T1053_005_OnLogon" ... & schtasks /create /tn "T1053_005_OnStartup" ...`. This is a high-signal cross-event view: the parent commandline alone reveals the entire two-task attack pattern before the second EID 1 event has even landed. In a real intrusion the parent could be `winword.exe` (Office macro spawning schtasks is a textbook initial-access-to-persistence chain), `wscript.exe`, `mshta.exe`, or an unexpected service process — any of those parents around an `schtasks /Create /RU SYSTEM` is a near-certain incident.
- **`CurrentDirectory: C:\Users\analyst\AppData\Local\Temp\`** — ART's staging directory. In a real intrusion, an `schtasks` invocation whose parent CWD is `\Temp\`, `\AppData\Local\`, or `\Downloads\` is itself a triage signal: legitimate scheduled-task creators (installers, system services, vendor updaters) typically run from `System32` or a vendor install path.
- **`User: DESKTOP-0DU4BT6\analyst`** + `/ru system` in the command line — non-privileged user creating a SYSTEM-run task. Textbook persistence + privilege-escalation. The primary SPL surfaces this as `suspicious_run_as=yes`; the secondary SPL surfaces it even cleaner as `subject_user=analyst` paired with `task_user_id=S-1-5-18`.
- **`IntegrityLevel: High`** — required to create a SYSTEM-run task. The `analyst` account is in the local Administrators group, so the elevated PowerShell session ran at High integrity and `schtasks` inherited. A medium-integrity user attempting `/RU SYSTEM` would fail with `ERROR: Access is denied.` — so seeing this exact pattern from a medium-integrity parent is itself a UAC-bypass or token-theft signal.
- **`task_run` (extracted from CommandLine) = `cmd.exe /c calc.exe`** — benign payload for the lab. In a real attack this field would contain the actual payload (a downloaded loader, a base64 PowerShell blob, a path to a dropped binary). It's the highest-signal field for triage.
