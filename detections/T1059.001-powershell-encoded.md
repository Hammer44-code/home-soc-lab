# Detection: PowerShell Encoded Command Execution

## MITRE ATT&CK

- **Tactic:** Execution (TA0002)
- **Technique:** T1059 — Command and Scripting Interpreter
- **Sub-technique:** T1059.001 — PowerShell

## Severity

**High** — Encoded PowerShell is a strong behavioral indicator of malicious activity. Legitimate administrators occasionally use `-EncodedCommand`, but it is heavily overrepresented in malware, post-exploitation frameworks (Empire, Cobalt Strike, Sliver), and phishing payloads because Base64 hides the inner command from casual log review and bypasses simple keyword-match filters.

## Detection Logic

```spl
index=endpoint sourcetype="WinEventLog:Microsoft-Windows-Sysmon/Operational" EventCode=1
(Image="*\\powershell.exe" OR Image="*\\pwsh.exe" OR OriginalFileName="PowerShell.EXE")
| where match(CommandLine, "(?i)\s-(encodedcommand|encodedcomman|encodedcomma|encodedcomm|encodedcom|encodedco|encodedc|encoded|encode|encod|enco|enc|en|e)\s")
   OR match(CommandLine, "(?i)FromBase64String")
| eval encoded_blob=coalesce(
    mvindex(split(CommandLine, " "), -1),
    "n/a")
| table _time host User ParentImage Image CommandLine encoded_blob Hashes
| sort - _time
```

### What each piece does

- `EventCode=1` — Sysmon "Process Create". Every spawned process is logged, with full command line.
- `Image="*\\powershell.exe"` matches the legacy Windows PowerShell. `pwsh.exe` covers PowerShell 7+. `OriginalFileName` catches renamed binaries (attackers sometimes copy `powershell.exe` to `notpowershell.exe` to evade Image-based detections — Sysmon records the PE header's original name regardless).
- The `match()` regex catches every valid abbreviation of `-EncodedCommand` from `-E` through the full word. PowerShell accepts any unambiguous prefix of a parameter, so an attacker can save bytes (and reduce signature surface) by using `-E` instead of `-EncodedCommand`. The regex anchors on whitespace before *and* after the flag, which ensures it's a standalone CLI argument — that's what prevents false matches against unrelated strings like `-EncodedCommandParamVariation` (a parameter name used by test harnesses).
- The second `match()` catches `FromBase64String` — the inline Base64 decode method used inside PowerShell scripts (a common pattern when the encoded payload is in a string rather than on the command line).
- `encoded_blob` extracts the last token from the command line — usually the Base64 payload itself. This is what an analyst would copy and decode during triage.
- `Hashes` shows the SHA256 of the powershell.exe binary; useful for confirming the legit Microsoft binary was used (vs a renamed copy with a different hash).

## Tuning Notes

This SPL is the second iteration. The first version used naive substring matching (`CommandLine="*-enc*"` etc.) and failed validation against Atomic Red Team's `T1059.001-15` test in two ways:

| Issue | Root cause | Fix |
|---|---|---|
| **False positive on test wrapper** | Pattern `*-EncodedCommand*` matched the string `-EncodedCommandParamVariation` (a parameter name used by the ART harness, not an actual flag). Substring match has no concept of word boundaries. | Switch from wildcard `*...*` substring match to regex `match()` with whitespace boundaries on both sides — the flag must be a standalone CLI argument. |
| **False negative on `-E` short form** | The test launched `powershell.exe -NoProfile -E <blob>`. No pattern in the original SPL matched the literal text `-E ` (hyphen-E-space). PowerShell accepts any unambiguous prefix down to a single letter, so attackers use the shortest one. | Alternation regex listing every valid prefix of `-EncodedCommand` from longest to shortest. Longest-first ordering ensures the engine matches the most specific variant available. |

**Validation:** After tuning, the SPL caught the real `-E <blob>` event (parent `WmiPrvSE.exe`, confirming WMI-based launch) and dropped the wrapper false positive. See the Sample Event below for the captured detection.

**Generalizable lesson:** Substring matching on CLI flags is fragile because parameters can appear (a) as standalone arguments, (b) as substrings of other parameter names, or (c) inside string literals or comments. Always anchor on whitespace or use regex word boundaries when the field is a command line.

## Why This Works

Attackers encode PowerShell commands for three reasons: (1) to slip past command-line keyword detections that look for strings like `IEX`, `DownloadString`, or `Invoke-Mimikatz`; (2) to safely pass multi-line scripts as a single shell argument; (3) to hide the payload from casual log review. The catch — from a defender's perspective — is that the flag itself (`-EncodedCommand`) is the giveaway. The attacker can encode the *contents* of the command, but they cannot encode the *flag that tells PowerShell to decode*. That argument is always visible in the process command line, and Sysmon Event ID 1 captures it verbatim before PowerShell ever begins execution.

This is a "tripwire" detection. It does not try to determine intent — it surfaces every encoded PowerShell invocation, and the analyst decides. Even if you cannot decode every blob during triage, the volume is low enough in a typical endpoint that each one warrants a glance.

## False Positive Considerations

Legitimate sources of encoded PowerShell exist and must be characterized for your environment:

- **System management tools** — SCCM/Intune, PDQ Deploy, Chocolatey, and some Group Policy preference items wrap their PowerShell payloads in `-EncodedCommand` to handle quoting cleanly. Identify these by their `ParentImage` (e.g., `ccmexec.exe`, `PDQDeployRunner.exe`) and whitelist the parent.
- **IDE / editor integrations** — VS Code's PowerShell extension launches encoded commands during debug sessions (parent `Code.exe` or `dotnet.exe`).
- **Windows itself** — A handful of built-in scheduled tasks under `\Microsoft\Windows\` use encoded PowerShell. Parent will be `taskeng.exe` or `svchost.exe` and the command will be stable; baseline once, exclude by exact command-line hash.
- **Cluster / monitoring agents** — Nagios, SolarWinds, and similar agents often run encoded probes.

**Tuning recommendations:**

1. Run this query over 7 days of baseline data in your environment.
2. Group by `ParentImage` and `CommandLine` to identify recurring legitimate encoded commands.
3. Add explicit exclusions to the SPL (e.g., `NOT ParentImage="*\\ccmexec.exe"`), commenting each one with the source you tuned out and the date — so future analysts know whether the exclusion is still valid.
4. Do **not** whitelist all of PowerShell ISE or all of VS Code — only the specific encoded-command patterns those tools produce. Otherwise an attacker who spawns powershell.exe from inside Code.exe (via a malicious extension or a child process injection) will evade.

### Analyst notes on this specific event

- **ParentImage = `WmiPrvSE.exe`** — PowerShell launched by the WMI Provider Service. In production, this pattern is a strong signal for **remote execution** via WMI (Impacket's `wmiexec.py`, `wmic /node:victim process call create`, or any C2 framework's WMI lateral-movement module). Real attackers use this exact telemetry shape during lateral movement.
- **`-NoProfile` + `-E` combination** — two evasion flags stacked. `-NoProfile` skips loading the user's PowerShell profile (avoiding logging hooks defenders may have planted there); `-E` is the shortest variant of `-EncodedCommand`, minimizing signature surface for keyword detections.
- **Decoded Base64 payload:** `Write-Host 3cf5511e-52ef-4892-ab35-e9fa122b1e79` (a UTF-16LE-encoded `Write-Host` of the test's GUID — benign, as expected for an ART validation test).
- **Decode it yourself in PowerShell:**
