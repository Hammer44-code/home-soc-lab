# Detection: Clear Windows Event Logs

> **Status: validated 2026-06-09.** Both searches fired end-to-end against hand-run clear commands on soc-victim. The **primary tripwire** returned exactly four rows — three EID 104 (`cleared_log=Application`) and one EID 1102 (`cleared_log=Security (audit log)`) — with the channel name correctly extracted and the clearer attributed (`DESKTOP-0DU4BT6\analyst` on 1102; the same subject SID on 104, see field-extraction calibration). The **secondary attribution** SPL classified all three process-spawning clears (`wevtutil cl` ×2, `powershell -Command "Clear-EventLog"` ×1) and correctly produced **no** row for the bare in-session `Clear-EventLog` cmdlet — the process-attribution blind spot, confirmed live. Validation also surfaced a real false positive (Windows Defender platform-update `wevtutil install-manifest` calls) that drove a hardening change to the secondary; see False Positive Considerations. The Sample Event below is a real captured EID 1102.
>
> **Note on tooling (2026-06-09):** the current Atomic Red Team catalog has **removed the standalone `T1070.001` atomics** — upstream ships only `T1070` (two FSUtil tests) and `T1070.003`–`.008`; there is no longer a `wevtutil cl` / `Clear-EventLog` atomic to invoke. This detection was therefore validated with **hand-run equivalent commands** (see Test Case), which is the cleaner approach here anyway: log-clearing "atomics" were always thin one-line wrappers around native binaries, and running them directly gives precise control over *which* logs are cleared.

## MITRE ATT&CK

- **Tactic:** Defense Evasion (TA0005)
- **Technique:** T1070.001 — Indicator Removal: Clear Windows Event Logs

## Severity

**High.** Unlike `cmd.exe` ([T1059.003](T1059.003-windows-command-shell.md)) or account discovery ([T1087](T1087-account-discovery.md)), clearing the Windows event log has **almost no benign cause on a running endpoint**. Normal log lifecycle is *rotation* and *auto-backup* (the service archives a full log and starts a fresh one — EID 1104), never a manual wipe. A deliberate `wevtutil cl` / `Clear-EventLog` is an anti-forensic action taken by an operator who wants their tracks gone — it sits squarely in the kill chain *after* the interesting activity, which is exactly why it's worth a high-confidence alert. This is the lab's first **single-sharp-signature** detection (contrast the burst model of T1087/T1082 and the weighted-score model of T1059.003 — [cheatsheet §10](../notes/splunk-spl-cheatsheet.md)): no scoring is needed because the event class *is* the malice.

## Detection Logic

The technique gives us a rare luxury — **two independent, high-fidelity, tool-agnostic event signals plus a process-attribution signal**:

| Signal | Channel / EID | Fires when | Catches |
|---|---|---|---|
| **Security audit log cleared** | `WinEventLog:Security` **EID 1102** | The **Security** log specifically is cleared | The clear, regardless of *how* (wevtutil, PowerShell, WMI, API) |
| **Event log cleared** | `WinEventLog:System` **EID 104** | **Any other** channel (System, Application, Sysmon/Operational, PowerShell/Operational, …) is cleared | The clear of a non-Security log, regardless of how |
| **Clear command executed** | Sysmon **EID 1** | A clear-log *binary/cmdlet* runs | The intent + **process attribution** (who/what/parent) |

EID 1102 and 104 are the **alert** — they're written by the Event Log *service itself* as the act of clearing completes, so they fire no matter which tool the adversary used (this is the same tool-agnostic "tripwire" logic as the T1547.001 EID 13 Run-key write — anchor on the *effect*, not the *actor*). EID 1 is the **attribution layer**: it can't see a clear performed by a tool that never spawns a tracked process (e.g., a direct API call from injected code), but when a process *is* involved it tells the analyst who did it and what their parent was.

### Primary — log-clear tripwire (the alert: EID 1102 + EID 104)

```spl
index=endpoint (
    (sourcetype="WinEventLog:Security" EventCode=1102)
    OR (sourcetype="WinEventLog:System" EventCode=104)
)
| rex field=_raw "(?i)The\s+(?<cleared_channel>[\w/\- ]+?)\s+log\s+file\s+was\s+cleared"
| eval cleared_log=case(
    EventCode=1102, "Security (audit log)",
    EventCode=104,  coalesce(cleared_channel, "non-Security log"),
    1=1,            "unknown"
  )
| eval method=if(EventCode=1102, "Security audit log cleared (EID 1102)", "Event log cleared (System EID 104)")
| eval clear_sid=coalesce(Security_ID, Sid)
| eval account=coalesce(Domain_Name."\\".Account_Name, Account_Name, clear_sid)
| table _time host account clear_sid cleared_log method EventCode
| sort - _time
```

**Field-extraction calibration (validated 2026-06-09 against the real events):**

- **EID 1102 auto-extracts the subject cleanly** — `Account_Name`, `Domain_Name`, and `Security_ID` come out as native fields *without* `Splunk_TA_windows`, so `account` resolves to `DESKTOP-0DU4BT6\analyst`. (1102 is far simpler than the 4624 logon events the [cheatsheet §2 gotcha](../notes/splunk-spl-cheatsheet.md) warns about — no `rex` needed.)
- **EID 104 carries only the SID, not the name.** The `Microsoft-Windows-Eventlog` 104 event has no `Account Name:` text — Splunk surfaces the clearer as the `Sid` field (`User` is just the `NOT_TRANSLATED` envelope). So `account` falls back to the raw SID via `coalesce`. Crucially that SID is **identical to the 1102 subject's `Security_ID`** (`S-1-5-21-…-1001` = `analyst`), so attribution is preserved — it's simply not name-resolved. Installing `Splunk_TA_windows` (Sprint 3 follow-up) adds the SID→name translation and `account` would render `analyst` here too. The `clear_sid` column is tabled explicitly so the analyst always has the attributable identifier even when the name is unresolved.
- **Only one `rex` survives** — `cleared_channel`, pulling the wiped channel name out of the 104 message ("The *Application* log file was cleared"). This matched on the first try.

### Secondary — clear-command attribution (Sysmon EID 1)

```spl
index=endpoint sourcetype="WinEventLog:Microsoft-Windows-Sysmon/Operational" EventCode=1
(CommandLine="*wevtutil*" OR CommandLine="*Clear-EventLog*" OR CommandLine="*cleareventlog*"
 OR CommandLine="*Remove-EventLog*" OR CommandLine="*Limit-EventLog*" OR CommandLine="*deletejournal*"
 OR CommandLine="*EventLog*.Clear()*")
| eval method=case(
    match(Image, "(?i)\\\\wevtutil\.exe$")  AND match(CommandLine, "(?i)\s(cl|clear-log)\b"), "wevtutil clear-log",
    match(CommandLine, "(?i)\bClear-EventLog\b"),  "PowerShell Clear-EventLog",
    match(CommandLine, "(?i)\bRemove-EventLog\b"), "PowerShell Remove-EventLog",
    match(CommandLine, "(?i)\bLimit-EventLog\b"),  "PowerShell Limit-EventLog (retention tamper)",
    match(Image, "(?i)\\\\wmic\.exe$") AND match(CommandLine, "(?i)cleareventlog"), "WMIC ClearEventLog",
    match(CommandLine, "(?i)EventLog.*\.Clear\(\)"), "PowerShell .NET EventLog.Clear()",
    match(Image, "(?i)\\\\fsutil\.exe$") AND match(CommandLine, "(?i)usn\s+deletejournal"), "fsutil USN journal delete"
  )
| where isnotnull(method)
| eval acct=coalesce(mvindex(mvfilter(User!="NOT_TRANSLATED"),0), User)
| table _time host acct method Image ParentImage CommandLine ParentCommandLine
| sort - _time
```

> **Why `| where isnotnull(method)` instead of a `1=1` catch-all.** The first draft ended the `case` with `1=1, "other log-clear indicator"` to surface unanticipated variants. Lab validation (2026-06-09) showed that catch-all is a **false-positive magnet**: a routine **Windows Defender platform update** spawns ~25 `wevtutil.exe install-manifest` / `uninstall-manifest` calls (re-registering ETW manifests for the updated `MpClient.dll`/`MpRtp.dll`/etc.), all parented by `MsMpEng.exe` and running as `SYSTEM`. `wevtutil` is not only a log-clear tool — and a `*wevtutil*` filter with a permissive catch-all scoops up every manifest (de)registration. Requiring a *positive* method classification and dropping nulls eliminates the entire class. The **primary** 1102/104 tripwire remains the safety net for any genuinely novel clear method this classifier doesn't name — see [cheatsheet §3](../notes/splunk-spl-cheatsheet.md) (anchor on the verb, not the binary).

### What each piece does

- **EID 1102 (Security log cleared).** The single highest-fidelity signal in this whole lab. The Event Log service writes 1102 as the *first* record of the freshly emptied Security log — so the clear announces itself. Effectively zero benign rate on an endpoint.
- **EID 104 (other log cleared).** The System-channel sibling, written by `Microsoft-Windows-Eventlog` whenever a *non*-Security channel is cleared. Crucially this includes clears of `Microsoft-Windows-Sysmon/Operational` and `...PowerShell/Operational` — i.e., an adversary clearing the very logs this lab's other detections depend on still trips *this* detection.
- **`cleared_channel` rex.** Pulls the channel name out of the 104 message so the analyst sees *which* log was wiped at a glance, not just "a log was cleared."
- **Binary classified off `Image`, arguments off `CommandLine`** — the recurring lab lesson ([cheatsheet §3](../notes/splunk-spl-cheatsheet.md), T1087 fix #1): `wevtutil`, `wmic`, `fsutil` matched on `Image`; the `cl`/`clear-log` verb and cmdlet names matched on `CommandLine`. The leading `CommandLine="*...*"` filters are cheap index-time narrowing; the `match()` in `method` does the precise, whitespace-anchored classification.
- **`\s(cl|clear-log)\b` whitespace anchor** — `wevtutil`'s clear verb is `cl` (or the long form `clear-log`). Substring-matching `cl` would match half the words in any path; the anchor forces it to be the standalone verb token (the [cheatsheet §3](../notes/splunk-spl-cheatsheet.md) flag-matching discipline).
- **`Limit-EventLog` (retention tamper).** Not a clear per se, but setting a log's max size to a tiny value forces near-immediate rollover — a quieter cousin of clearing. Included as a low-noise bonus indicator.
- **`acct` dedup** — the multivalued-`User` coalesce ([T1087 fix #2](T1087-account-discovery.md)).

## Why This Works

The deepest point of this detection is that **log clearing is futile against a forwarding SIEM — and the act of trying generates its own alarm.** The Splunk Universal Forwarder ships each event off the host the moment it's written; by the time an adversary runs `wevtutil cl`, the events they're trying to erase are already sitting in `index=endpoint` on a separate machine they don't control. Worse for them, the clear *itself* produces EID 1102/104, which forwards too. So the anti-forensic technique inverts into a **high-confidence detection signal**: the attacker has told us exactly when they decided to cover their tracks, which is some of the most valuable timeline information in an investigation.

That's also why no scoring or correlation is needed here. With `cmd.exe` the malice was in subtle combinations of parentage and payload; here the event class is intrinsically suspicious. The detection's job is simply to *not miss it* — hence two redundant tool-agnostic signals (1102 + 104) backed by process attribution (EID 1).

## Tuning Notes

**Pre-flight calibration:**

- **Step zero is different here.** For prior detections, step zero was "confirm the event class is in the index." But 1102 and 104 are *only* emitted when a log is actually cleared — so a baseline `stats count` will (correctly) return **0** until the test runs. The right pre-flight is instead to confirm the **channels are being collected**: `index=endpoint sourcetype="WinEventLog:Security" | stats count` and `... sourcetype="WinEventLog:System" | stats count` should both be non-zero. Confirmed at validation (Security 246, System 39). The 1102/104 appear only *after* the clear.

**Validation findings (2026-06-09) — what the real events taught us:**

- **104 message format confirmed.** The `cleared_channel` rex matched "The *Application* log file was cleared" on the first try — the literal wording held on this Win10 22H2 build. (`coalesce(..., "non-Security log")` remains as a fallback for localized/reworded builds.)
- **1102 needs no `rex` — it auto-extracts.** Splunk surfaces `Account_Name`, `Domain_Name`, and `Security_ID` as native fields on the 1102 event, so the planned Security-channel `_raw` rex (§7) was dropped. The original draft's `Account Domain:` rex would in fact have *failed* — the 1102 message labels the field `Domain Name:`, not `Account Domain:` — but it never mattered because the auto-extracted fields supersede it.
- **104 attribution is SID-only without the TA.** The 104 event carries no account *name* — only `Sid` (the clearer's SID) and the `NOT_TRANSLATED` envelope. The detection tables that SID (`clear_sid`); it matches the 1102 subject exactly, so the clearer is still attributable. Name resolution waits on `Splunk_TA_windows`.
- **Process-attribution blind spot, confirmed live.** Of the four clear actions run, the three that spawned a process (two `wevtutil cl`, one `powershell -Command "Clear-EventLog"`) appeared in the secondary; the bare in-session `Clear-EventLog` cmdlet produced **no** EID 1 at all — exactly the false-negative class below. The primary 104 fired for it regardless, which is the whole argument for the event-tripwire being the alert.
- **Lab harness note (no ART here):** because these were hand-run from an interactive elevated PowerShell, the `wevtutil`/`powershell` clears were parented by `powershell.exe`. In a real intrusion the parent is the interesting field; here it's the operator shell. (Had we used ART, the [cheatsheet §10 caveat](../notes/splunk-spl-cheatsheet.md) — everything parented by the ART runner — would apply identically.)

**Known false-negative classes:**

- **Direct-API clears.** Code that calls `EvtClearLog`/`ClearEventLog` Win32 APIs from inside an existing process (injected shellcode, a malicious service DLL) spawns no new process, so the **secondary** SPL misses it — but the **primary** 1102/104 tripwire still fires, because the service writes those regardless of caller. This is exactly why the event-based tripwire is the alert and the process layer is only attribution.
- **Selective deletion vs. full clear.** An adversary using a tool like `DeleteRecord`/EventCleaner to surgically remove *individual* records (rather than clearing the whole log) produces **no** 1102/104 — the log is never "cleared." That's an advanced anti-forensic technique out of scope for this detection; it's caught instead by sequence-gap analysis (RecordNumber discontinuities), a future hunt.

## False Positive Considerations

The benign rate is genuinely near zero, but the handful of real causes:

- **Imaging / sysprep / VM provisioning.** Building or cloning a host often clears logs as part of generalization. Identifiable by timing (provisioning window) and account (`SYSTEM`/imaging service). Allowlist the maintenance window, not the technique.
- **Backup/archival tooling that clears after export.** Some compliance agents clear a log once it's been archived. Baseline the specific service account and host; suppress that account, not the alert.
- **A genuine admin troubleshooting.** Occasionally an admin clears the Application log to reproduce a clean error. Rare, attributable, and worth a quick confirm-with-the-human rather than a silent allowlist.
- **Windows Defender platform updates (the secondary's real FP — caught in lab 2026-06-09).** Each Defender platform upgrade has `MsMpEng.exe` shell out to ~25 `wevtutil.exe install-manifest` / `uninstall-manifest` calls (re-registering the ETW manifests for `MpClient.dll`, `MpRtp.dll`, `NisSrv.exe`, `WdFilter.sys`, …) as `SYSTEM`. These are **`wevtutil` but not clears** — the reason the secondary SPL classifies on the `cl`/`clear-log` verb and drops everything else (`| where isnotnull(method)`) rather than flagging the binary. They never produce 1102/104, so the **primary** tripwire is unaffected; this FP is specific to a binary-name-based process filter.
- **Not a clear — don't confuse:** EID **1100** (Event Log service shutting down) fires on every clean reboot; EID **1104** (the security log is full) fires on auto-backup rollover. Neither is in this detection's scope — only 1102 (manual/programmatic Security clear) and 104 (manual/programmatic other-log clear).

**Tuning recommendations:**

1. **Alert on the primary (1102+104); use the secondary for attribution and IR pivot.** When 1102 fires, immediately run the secondary over a ±5-minute window to find the *process* that did it and its parent.
2. **Allowlist by account, not by event.** The legitimate causes are tied to specific service/imaging accounts; suppress those principals rather than weakening the tripwire.
3. **Correlate forward in time.** A log clear is rarely the *start* of activity — it's the cleanup. Pivot *backward* from the 1102 timestamp through `index=endpoint` (which the forwarder preserved) to reconstruct what the adversary was erasing.

## Test Case

ART no longer ships T1070.001 atomics (see the status note), so we validate by hand-running the native clear commands in an **elevated PowerShell** on soc-victim. These *are* the commands the old atomics wrapped — running them directly is equivalent telemetry with precise control over which logs we touch.

> **⚠️ Operational caveat unique to this technique:** these commands *actually clear real logs* on soc-victim — including, for the EID 1102 proof, the Security log. **That destroys local event history**, but **already-forwarded events in `index=endpoint` are safe** (that's the whole "Why This Works" point). We deliberately clear the **Application** log for the EID 104 / attribution tests (least-useful history), and clear **Security** exactly once, knowingly, to prove EID 1102 — it wipes the local logon history that upcoming logon-based detections might want, but nothing forwarded is lost.

```powershell
# Elevated PowerShell on soc-victim. No ART import needed — these are native commands.

# (1) wevtutil clears a non-Security log -> EID 104 + a NEW wevtutil.exe process (EID 1)
wevtutil cl Application

# (2) Clear-EventLog as a fresh process -> EID 104 + a NEW powershell.exe whose
#     CommandLine carries "Clear-EventLog" (EID 1, method="PowerShell Clear-EventLog")
powershell.exe -Command "Clear-EventLog -LogName Application"

# (3) Clear-EventLog as a BARE cmdlet in this same session -> EID 104 fires,
#     but NO new process is spawned, so the secondary (EID 1) sees NOTHING.
#     This deliberately demonstrates the process-attribution blind spot.
Clear-EventLog -LogName Application

# (4) THE EID 1102 PROOF — clears the Security audit log. Run knowingly (see caveat).
wevtutil cl Security
```

**Predicted signal mapping** (the validation criterion):

| Command | Primary tripwire | Secondary attribution (`method=`) |
|---|---|---|
| (1) `wevtutil cl Application` | **EID 104**, `cleared_log=Application` | `wevtutil clear-log` ✓ |
| (2) `powershell -Command "Clear-EventLog ..."` | **EID 104**, `cleared_log=Application` | `PowerShell Clear-EventLog` ✓ (fresh process) |
| (3) bare `Clear-EventLog` in-session | **EID 104**, `cleared_log=Application` | **(nothing)** — no new process, the documented blind spot |
| (4) `wevtutil cl Security` | **EID 1102**, `cleared_log=Security (audit log)` | `wevtutil clear-log` ✓ |

Commands (2) and (3) are the key teaching pair: **both trip the primary 104 tripwire, but only the fresh-process form (2) appears in the secondary.** That's the live proof of why the event-based tripwire — not the process layer — is the alert (the API-clear false-negative class in Tuning Notes). *(Optional extras if you want more `method=` coverage: `wmic nteventlog where logfilename='Application' call cleareventlog` for the WMIC branch — note `wmic` is deprecated and may be absent on newer builds; `fsutil usn deletejournal /D C:` for the USN branch, though that's really the T1070-parent FSUtil behaviour.)*

**To validate end-to-end:**

1. Confirm the VM clock reads Central; note wall-clock time.
2. **Step zero (adapted):** confirm both channels are collecting — `index=endpoint sourcetype="WinEventLog:Security" | stats count` and `... sourcetype="WinEventLog:System" | stats count` both non-zero. (The 1102/104 themselves appear only *after* a clear — don't expect them in a baseline.)
3. Run commands (1)–(4) above, in order.
4. Run the **primary** tripwire ("Last 15 minutes") — confirm **four** rows: three EID 104 (`cleared_log=Application`) and one EID 1102 (`cleared_log=Security (audit log)`). The 1102 `account` resolves to `DESKTOP-0DU4BT6\analyst`; the 104 rows show the same subject as a raw SID in `clear_sid` (no name without the TA).
5. Run the **secondary** attribution SPL — confirm **three** rows (commands 1, 2, 4), correctly classified, and that command (3) produced **no** EID 1 row — the blind spot, confirmed live. Also confirm no `wevtutil install-manifest` noise from a recent Defender update slips in (it shouldn't, post-hardening — see False Positive Considerations).
6. Cleanup: nothing to undo — the logs are already cleared (that *was* the test). Local history before the test window now lives only in Splunk.

### Analyst notes on these real events

- **`Message=The audit log was cleared.` (1102) / `The Application log file was cleared.` (104)** — the canonical strings. That single line *is* the alert; everything else is attribution.
- **`Subject: Account Name: analyst` (1102)** — *who* cleared it, name-resolved. In a real intrusion this is the compromised/operator account; correlate against the 4624 logon that established the session.
- **The 104 carries only `Sid`, no name** — but `S-1-5-21-…-1001` is byte-for-byte the 1102 subject's `Security_ID`, so the clearer is fully attributable even on the non-Security channel; only the friendly name awaits `Splunk_TA_windows`. This is why the detection tables `clear_sid`.
- **The 1102 message labels the domain field `Domain Name:`, not `Account Domain:`** — the gotcha that would have broken a hand-written rex, sidestepped by using the auto-extracted `Domain_Name` field.
- **`SourceName=Microsoft-Windows-Eventlog` on both** — the events are written by the log service itself, not by `wevtutil`/`powershell` — which is exactly why the tripwire is tool-agnostic: any clear method produces them.
