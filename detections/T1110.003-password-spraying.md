# Detection: Brute Force — Password Spraying

> **Status: validated 2026-06-15.** The first **network-side** detection in this lab — the attack traffic originated on the soc-kali VM (`192.168.56.30`) and crossed the wire to the soc-victim (`192.168.56.20`), rather than running locally via Atomic Red Team. A real password spray with [NetExec](https://github.com/Pennyw0rth/NetExec) (`nxc smb`) against six local accounts produced **five `4625` failed logons + one `4624` success** (the `analyst` account, whose real password was the sprayed value). Both SPLs fired end-to-end: the burst SPL isolated the spray (`distinct_targets=5`, `src=192.168.56.30`) out of background logon noise, and the success-correlation SPL self-escalated to **CRITICAL** and named `analyst` as the compromised account. This is also the first detection to run against the `Splunk_TA_windows`-normalized `sourcetype=WinEventLog` (see [lab notes](../README.md)).

## MITRE ATT&CK

- **Tactic:** Credential Access (TA0006)
- **Technique:** T1110 — Brute Force
- **Sub-technique:** T1110.003 — Password Spraying

Password spraying inverts the classic brute force. Instead of many passwords against **one** account (which trips account-lockout fast), the attacker tries **one** password (e.g. `Sledge44`, `Spring2026!`, `Password1`) against **many** accounts. Each account sees only one or two failures — under the lockout threshold — but the attacker covers the whole user population in a single pass, betting that *someone* reuses a weak/common password. It is one of the most common initial-access and lateral-movement techniques precisely because it is quiet at the per-account level.

## Severity

**Medium → Critical, depending on outcome.** A spray that produces only failures is a **Medium/High** "someone is hammering our accounts from one host" alert. A spray where one guess **lands** — a `4624` success from the same source IP inside the same burst of failures — is **Critical**: the attacker now holds valid credentials and is authenticated. This detection ships two SPLs so the alert can self-escalate: a burst SPL (the attempt) and a success-correlation SPL (the compromise).

## Detection Logic

The detectable shape of a spray in Windows logon telemetry is **one source address generating failed logons against many *distinct* target accounts in a short window.** The password itself is never in the logs — so the signal is not "wrong password" but the **fan-out**: a single origin touching account after account.

Both searches key off Windows Security events, now indexed under the `Splunk_TA_windows`-normalized `sourcetype=WinEventLog`:

- **EID 4625** — failed logon (the spray body)
- **EID 4624** — successful logon (the buried hit, for escalation)
- `Logon_Type=3` — network logon (SMB/RDP/etc.), which is how a remote spray arrives. Scoping to Type 3 cuts out the constant background of Type-5 *service* logons.

### Primary — spray burst (the attempt)

```spl
index=endpoint sourcetype=WinEventLog EventCode=4625 Logon_Type=3
| eval target=mvindex(mvfilter(Account_Name!="-"),0)
| where isnotnull(target)
| bin _time span=5m
| stats dc(target) as distinct_targets values(target) as targets count as failures by _time src
| where distinct_targets >= 3
| sort - _time
```

### Secondary — success correlation (the compromise / self-escalation)

```spl
index=endpoint sourcetype=WinEventLog (EventCode=4625 OR EventCode=4624) Logon_Type=3
| eval target=mvindex(mvfilter(Account_Name!="-"),0)
| eval outcome=if(EventCode=4624,"success","failure")
| where isnotnull(target)
| bin _time span=5m
| stats dc(eval(if(outcome="failure",target,null()))) as failed_targets
        values(eval(if(outcome="failure",target,null()))) as failed_users
        values(eval(if(outcome="success",target,null()))) as compromised
        count(eval(outcome="failure")) as failures
        count(eval(outcome="success")) as successes
        by _time src
| where failed_targets >= 3
| eval severity=if(successes>0,"CRITICAL - spray succeeded","HIGH - spray attempt")
| table _time src severity failed_targets failed_users successes compromised failures
| sort - _time
```

### What each piece does

**Primary (burst):**

- Scopes to `EID 4625` + `Logon_Type=3` — remote failed logons only.
- `eval target=mvindex(mvfilter(Account_Name!="-"),0)` extracts the *real* target account. `Account_Name` is **multivalued** on these events (the subject `-` plus the target); the `mvfilter` drops the `-` and keeps the account. The same idiom collapses the multivalued `User` field in the discovery detections ([T1087](T1087-account-discovery.md)).
- `where isnotnull(target)` drops the **anonymous SMB session-setup probes** — each `nxc` run opens a null session to fingerprint the host, which logs a `4625` with `Account_Name=-` only. Filtering null targets removes them so they don't inflate the count.
- `bin _time span=5m` + `stats dc(target) ... by _time src` counts **distinct target accounts per source IP per 5-minute bucket**. This is the burst-correlation idiom (same family as [T1087](T1087-account-discovery.md)/T1082), but keyed on `src` + distinct *accounts* instead of distinct *commands*.
- `where distinct_targets >= 3` is the alert threshold. **The discriminator that defeats false positives is "distinct accounts," not "failure count":** one user fat-fingering their own password generates many failures against **one** account; a spray generates failures against **many** accounts from **one** source. A real user can't reach 3 distinct accounts.

**Secondary (success correlation):**

- Same scope but pulls in `EID 4624` too, tagging each event `outcome=success|failure`.
- The conditional aggregations (`dc(eval(if(outcome="failure",...)))`, `values(eval(if(outcome="success",...)))`) split the single event stream into the failure wall and the success(es) **per source IP per bucket** in one pass.
- `severity=if(successes>0, "CRITICAL...", "HIGH...")` makes the alert escalate itself: a burst of distinct-account failures *with* a co-located success from the same IP means the spray worked.
- `compromised` **names the account that fell** — the single most important field for the responder, who now has to assume that account is attacker-controlled and start containment.

## Why This Works

Authentication is a chokepoint. To use a credential the attacker must *present* it, and every presentation against a Windows host is logged — `4625` on failure, `4624` on success, both carrying the **source network address** on network logons. The attacker cannot spray without generating these events; there is no quieter API path the way there is for some discovery techniques.

The per-account stealth that makes spraying effective against lockout policies is exactly what **exposes** it at the aggregate level. By spreading one password across many accounts, the attacker keeps each account under the lockout threshold — but concentrates all of that activity behind **one source IP in a short window**, which is a glaring anomaly when you pivot the view from "per account" to "per source." The defender's leverage is the aggregation: a single origin fanning out across the user population is a shape that legitimate authentication essentially never produces.

The success-correlation layer adds the part a SOC actually pages on. Failures alone are noise-adjacent; a failure wall *with a hit inside it* is an active compromise, and the detection draws that line automatically.

## Tuning Notes

Validated end-to-end on 2026-06-15. The spray was generated from soc-kali with NetExec:

```bash
printf '%s\n' analyst administrator admin guest user jsmith > ~/users.txt
nxc smb 192.168.56.20 -u ~/users.txt -p Sledge44 --continue-on-success
```

`analyst:Sledge44` is a real local credential (so it succeeds → the buried `4624`); the other five fail → the `4625` wall. The burst SPL returned a single row — `src=192.168.56.30`, `distinct_targets=5`, all five failed accounts, `failures=5`. The success-correlation SPL returned `severity=CRITICAL - spray succeeded`, `compromised=analyst`. Several calibration findings, all from live data:

**`src` populates on `Logon_Type=3` (resolved open question).** When `Splunk_TA_windows` was installed (2026-06-12), `src` was **blank** on all historical events because they were Type-5 *service* logons, which have no source network address — and it was an open question whether `src` would populate on real network logons. This spray confirmed it: every Type-3 `4625`/`4624` carried `src=192.168.56.30` **and** the redundant `Source_Network_Address=192.168.56.30`. Source-IP attribution — the field that makes this alert actionable — works. `src` is the TA's CIM-normalized alias; either field can be used.

**`Account_Name` is multivalued (`-` subject + real target).** Grouping naively would split or mislabel rows. `mvindex(mvfilter(Account_Name!="-"),0)` collapses it to the target account. Same field-shape quirk as the multivalued `User` field in [T1087](T1087-account-discovery.md) — worth assuming multivalue on any account field from this index.

**The anonymous host-enum probe is a second `4625` per run.** Each `nxc smb` invocation opens a null/anonymous SMB session to fingerprint the host (the `[*] Windows 10 ... Build 19041` banner line), which logs a `4625` with `Account_Name=-` and `Sub_Status=0x0`. Two `nxc` runs → two of these. `where isnotnull(target)` discards them so they don't pad `distinct_targets`. Good to know they exist — on their own they're a (very) low-signal "someone null-session-probed SMB" indicator.

**`Sub_Status` leaks account validity — a bonus enumeration signal.** The failure sub-status distinguishes *which usernames are real*:

| Sub_Status | Meaning | Spray result |
|------------|---------|--------------|
| `0xC0000064` | STATUS_NO_SUCH_USER | `admin`, `user`, `jsmith` — **do not exist** |
| `0xC000006A` | STATUS_WRONG_PASSWORD | `administrator`, `guest` — **exist**, password wrong |

So the spray simultaneously performs **user enumeration**: the `0xC000006A` accounts are confirmed valid targets for a follow-up focused attack. A triage analyst should treat the wrong-password accounts as the real exposure. A future enrichment could surface `Sub_Status` decoded in the alert.

**Spray tools stop on first hit by default (tool-behavior caveat).** NetExec's first run **halted after `analyst` succeeded** (it was first in the user list) and never tried the other five — producing the `4624` success but **zero** `4625`s. The full failure wall only appeared after re-running with `--continue-on-success`. Lesson for both attacker emulation and triage: the "all failures then a success" ordering you see in logs is shaped by tool behavior and user-list order, not a law of nature — don't assume the failures always precede the success.

**Threshold (`distinct_targets >= 3`).** Set low for this six-account lab (fires clearly at 5). In production, tune to the user population — a spray usually hits **dozens** of accounts, so `>= 10` is a more typical operational threshold that still sits far above any legitimate single-source failure pattern. Start at your baseline's 99th percentile of distinct-accounts-failed-per-source and adjust.

**Bin-boundary fragility (accepted, inherited from the burst idiom).** `bin _time span=5m` means a spray straddling a 5-minute boundary can split its distinct-account count across two buckets. In the lab the whole spray landed in the 19:10 bucket and fired cleanly. A `streamstats` sliding window is the production-hardened form — noted, not changed here for SPL readability (same trade-off documented in [T1087](T1087-account-discovery.md)).

## False Positive Considerations

Legitimate sources of multi-account failed logons from a single host:

- **Misconfigured service accounts / scheduled tasks** with a stale password retrying against several resources after a password rotation. These usually repeat against the **same** account(s), so `distinct_targets` stays low — the threshold filters them.
- **Vulnerability scanners / pentest tooling** (Nessus, Qualys with credentialed scans, an authorized engagement) authenticating broadly. Allowlist the known scanner `src`.
- **A user mistyping after a password change** — hits **one** account; cannot reach `distinct_targets >= 3`.
- **Backup / management / monitoring agents** authenticating to many hosts with one service identity (more relevant in a multi-host environment).

**Tuning recommendations:**

1. **Alert on the burst, page on the success correlation.** Distinct-account failures are worth an alert; a co-located success is worth a call.
2. **Allowlist known scanner and management `src` addresses** — but log-and-review them, don't blanket-suppress.
3. **Tune `distinct_targets` to your population** (see Tuning Notes) and consider a per-source rate (failures/minute) as a secondary condition.
4. **Enrich with `Sub_Status`** to separate "spraying random names" (mostly `0xC0000064`) from "spraying known-valid accounts" (`0xC000006A`) — the latter is higher-confidence and often a *second-stage* spray after enumeration.
5. **Chain tactics.** A spray success (`4624`) immediately followed by discovery ([T1087](T1087-account-discovery.md)/T1082), credential access ([T1003](T1003.001-lsass-access.md)), or lateral movement on that host is a near-certain intrusion — a correlation search across these is a planned project extension.

## Test Case

Generated from the **soc-kali** attacker VM (`192.168.56.30`) against **soc-victim** (`192.168.56.20`) over the host-only network — no Atomic Red Team, because spraying is inherently a network-origin attack.

**Prerequisites:**

- soc-victim powered on, SMB (445) reachable from Kali: `nc -zv 192.168.56.20 445` → `open`.
- NetExec installed on Kali (ships in Kali 2025.2 as `nxc`): `nxc smb --version`.
- The victim must audit **logon failures** (`4625`). Confirmed on by checking `index=endpoint sourcetype=WinEventLog EventCode=4625 | stats count` returns non-zero *after* the spray; if zero, enable with `auditpol /set /subcategory:"Logon" /failure:enable` on the victim.

**Run the spray:**

```bash
# On soc-kali
printf '%s\n' analyst administrator admin guest user jsmith > ~/users.txt
nxc smb 192.168.56.20 -u ~/users.txt -p Sledge44 --continue-on-success
```

`--continue-on-success` is **required** — without it NetExec stops after the first valid credential and you get the success but not the failure wall (see Tuning Notes).

**To validate end-to-end:**

1. Confirm 445 is reachable and run the spray above; note the wall-clock time.
2. Expect six NetExec result lines — one green `[+] ...\analyst:Sledge44 (Pwn3d!)` and five red `[-] ... STATUS_LOGON_FAILURE`.
3. **Pre-flight count** (Last 15 min): `index=endpoint sourcetype=WinEventLog (EventCode=4625 OR EventCode=4624) Logon_Type=3 | stats count by EventCode` — confirm both `4625` and `4624` are present before iterating SPL (the "verify the data is in the index first" discipline).
4. Run the **primary** SPL — confirm one row: `src=192.168.56.30`, `distinct_targets=5`, `targets` listing the five failed accounts.
5. Run the **secondary** SPL — confirm `severity=CRITICAL - spray succeeded`, `compromised=analyst`.
6. Verify `src` populated with `192.168.56.30` on the Type-3 rows (the field that makes the alert attributable).

### Analyst notes on this real captured event

- **`Logon_Type: 3`** — network logon, the signature of a *remote* spray (SMB in this case). A local/console spray would be Type 2; RDP Type 10. Scoping the SPL to Type 3 removes the constant Type-5 service-logon background.
- **`Source Network Address: 192.168.56.30`** — Kali. This is the field the whole detection hangs on; on Type-3 logons it populates cleanly (it was blank on the historical Type-5 service logons — see Tuning Notes).
- **`Sub Status: 0xC000006A`** — STATUS_WRONG_PASSWORD: the account exists, only the password was wrong. The five sprayed non-`analyst` accounts split into this (real: `administrator`, `guest`) vs `0xC0000064` STATUS_NO_SUCH_USER (`admin`, `user`, `jsmith`) — free user enumeration as a side effect of the spray.
- **`Account Name: -` / target** — the subject is the null `-` (no authenticated subject on a failed network logon); the *target* account is what was sprayed. This is why `Account_Name` is multivalued and the SPL `mvfilter`s the `-` out.
- **`Status: 0xC000006D` vs `Sub Status: 0xC000006A`** — the top-level `Status` is the *generic* `STATUS_LOGON_FAILURE` (`0xC000006D`) and is the **same on every failed logon**, so it carries no discriminating information. The detail lives in `Sub_Status` (`0xC000006A` = wrong password vs `0xC0000064` = no such user). Triage on `Sub_Status`, not `Status`.
- **`user=administrator` — a clean single-valued CIM field from `Splunk_TA_windows`.** The TA normalizes the multivalued `Account_Name` down to a tidy `user` field. The validated SPLs above use the `mvfilter(Account_Name!="-")` form (portable to a no-TA index), but on this TA-equipped index the SPL could be simplified to `... | where user!="-" | stats dc(user) ... by _time src` — a cleaner equivalent. Likewise `action` (`failure`/`success`) is a CIM alternative to keying on `EventCode`. Noted as a simplification; the `Account_Name` form is what was run for validation.
- **`Logon_Process: NtLmSsp` / `Authentication Package: NTLM`** — the spray came in over **NTLM** (NetExec's SMB auth). A Kerberos-based spray (e.g. against a domain) would show `Kerberos` here — a future-DC extension. `app=win:remote` is the TA's tag for a remote logon attempt.
