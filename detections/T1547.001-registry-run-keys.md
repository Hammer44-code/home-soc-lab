# Detection: Registry Run Key Persistence

> **Status: validated 2026-06-03.** Fired end-to-end against Atomic Red Team `T1547.001-1` (HKCU Run) and `T1547.001-2` (HKLM RunOnceEx) on the soc-victim VM. The run also surfaced live OneDrive false positives and exposed two SPL bugs — see Tuning Notes. The Sample Event below is built from the real captured field values (only the Sysmon-internal ProcessGuid/ProcessId are reconstructed, as noted).

## MITRE ATT&CK

- **Tactic:** Persistence (TA0003)
- **Technique:** T1547 — Boot or Logon Autostart Execution
- **Sub-technique:** T1547.001 — Registry Run Keys / Startup Folder

This write-up covers the **Registry Run Keys** half of the sub-technique. The Startup Folder half (file drops into `...\Start Menu\Programs\Startup\`) is observable via Sysmon EID 11 and is noted in the False-Negative section as a complementary detection.

## Severity

**Medium** — Registry Run keys are the single most common persistence mechanism on Windows, used by virtually every commodity malware family and post-exploitation framework, and also by a large fraction of legitimately installed software (every app with a "start with Windows" option). Like scheduled tasks, this cannot be an "alert on any Run-key write" rule — it has to surface the *unusual* writes. Per-event triage is the model: every value set is logged, and the analyst looks at which key, the value name, and above all the **target path/binary** to decide.

## Detection Logic

The primary search keys off Sysmon **EID 13** ("Registry value set") where the modified registry value lives under a Run key. This is the catch-all: EID 13 fires on the registry write itself, so it captures the persistence **regardless of how it was created** — `reg.exe add`, PowerShell `Set-ItemProperty`, `New-ItemProperty`, or a direct `RegSetValueEx` API call from compiled malware all land here. A secondary command-line search on EID 1 adds attribution context (which process wrote the key) but only catches the `reg.exe` path, so it is a supplement, not the primary.

This is the mirror image of the T1053.005 design: there, the Security audit event (4698) was the tool-agnostic catch-all and the Sysmon process event was the supplement. Here, the Sysmon **registry** event is the catch-all and the process event is the supplement.

### Primary — Sysmon EID 13 on Run-key value writes

```spl
index=endpoint sourcetype="WinEventLog:Microsoft-Windows-Sysmon/Operational" EventCode=13
TargetObject="*CurrentVersion\\Run*" OR TargetObject="*Policies\\Explorer\\Run*" OR TargetObject="*CurrentVersion\\Windows\\Run*"
| rex field=TargetObject "(?i)\\\\(?<run_key>RunOnceEx|RunServicesOnce|RunServices|RunOnce|Run)\\\\(?<value_name>.+)$"
| eval hive=case(match(TargetObject,"(?i)^HKLM"),"HKLM (all users)", match(TargetObject,"(?i)^HKU"),"HKCU (per-user)", 1=1,"other")
| eval suspicious_path=if(match(Details, "(?i)(\\\\temp\\\\|\\\\appdata\\\\|\\\\programdata\\\\|\\\\users\\\\public\\\\|\\\\downloads\\\\|%temp%|%appdata%)"), "yes", "no")
| eval suspicious_target=if(match(Details, "(?i)(powershell|pwsh|cmd\.exe|rundll32|regsvr32|mshta|wscript|cscript|bitsadmin|certutil|-enc|-e\s|frombase64|iex|invoke-expression)"), "yes", "no")
| eval no_extension=if(match(Details, "(?i)\.(exe|dll|bat|cmd|ps1|vbs|js|scr|hta)\b"), "no", "yes")
| table _time host Image User run_key value_name Details hive suspicious_path suspicious_target no_extension TargetObject
| sort - _time
```

### Secondary — Sysmon EID 1 on `reg.exe add` to a Run key (attribution view)

```spl
index=endpoint sourcetype="WinEventLog:Microsoft-Windows-Sysmon/Operational" EventCode=1
Image="*\\reg.exe"
| where match(CommandLine, "(?i)\sadd\s") AND match(CommandLine, "(?i)CurrentVersion\\\\Run|Policies\\\\Explorer\\\\Run")
| rex field=CommandLine "(?i)/v\s+\"?(?<value_name>[^\"]+?)\"?\s+/t"
| rex field=CommandLine "(?i)/d\s+\"(?<value_data_q>[^\"]+)\""
| rex field=CommandLine "(?i)/d\s+(?<value_data_u>[^\"\s]\S*)"
| eval value_data=coalesce(value_data_q, value_data_u)
| table _time host User ParentImage Image value_name value_data CommandLine
| sort - _time
```

### What each piece does

**Primary SPL (EID 13):**

- The `TargetObject` filter scopes to the three Run-key families the Sysmon config monitors (see `setup/sysmon-config.xml` line ~623): the standard `...CurrentVersion\Run` family (which by `contains` also catches `RunOnce`, `RunOnceEx`, `RunServices`, `RunServicesOnce`), the policy-based `Policies\Explorer\Run`, and the legacy `CurrentVersion\Windows\Run`.
- `run_key` and `value_name` are extracted from the tail of `TargetObject`. The value name is attacker-controlled and often a tell — malware frequently uses a generic-looking name ("Windows Update", "Adobe", "OneDrive") to blend in, or a random string. The `run_key` alternation is ordered longest-first (`RunOnceEx` before `RunOnce` before `Run`) and `value_name` captures `.+` rather than a single path segment, so the nested `RunOnceEx\NNNN\Depend\N` DLL-dependency structure parses instead of blanking out — see Tuning Notes for the bug this replaced.
- `hive` distinguishes **HKLM** (writes here persist for *all users* and require local admin — higher signal) from **HKCU**, rendered by Sysmon as `HKU\<SID>\...` (per-user, no admin needed — the most common malware path because it works from a normal user token).
- `Details` is the value *data* — for a Run key this is the **command line that executes at logon**, the single highest-signal field. The three flag fields triage it:
  - `suspicious_path` — the target sits in a user-writable / non-standard directory (`\Temp\`, `\AppData\`, `\ProgramData\`, `\Users\Public\`, `\Downloads\`, or `%TEMP%`/`%APPDATA%` expansions). Legitimate autostart entries almost always point into `Program Files`, `System32`, or a vendor install path.
  - `suspicious_target` — the data invokes a LOLBin or an obvious script-exec pattern (`powershell -enc`, `rundll32`, `mshta`, `IEX`, base64, etc.). A Run key whose payload is `powershell.exe -enc <blob>` is rarely benign.
  - `no_extension` — the data references no recognizable executable/script extension, which can indicate an obfuscated or unusual loader (or, benignly, an entry that points at a registered handler — triage rather than alert).

**Secondary SPL (EID 1):**

- Scopes to `reg.exe` with an `add` operation targeting a Run path. This gives the **process attribution** the registry event lacks on its own: `ParentImage` (what spawned `reg.exe`), `User`, and the full command line. A Run-key write whose `reg.exe` was spawned by `winword.exe`, `mshta.exe`, `wscript.exe`, or an unexpected process is a near-certain incident.
- `/v` is the value name, `/d` is the data. `/d` uses the same two-pass quoted/unquoted `coalesce()` extraction as the T1053.005 `/TR` parser, for the same reason: a single alternation regex with duplicate group names is rejected by Splunk's PCRE2 (`PCRE2_DUPNAMES not set`).
- This SPL is **blind to non-`reg.exe` writes** — PowerShell's `Set-ItemProperty`/`New-ItemProperty`, the `.NET` registry classes, and direct API writes from compiled malware never spawn `reg.exe`. That is exactly why the EID 13 search is primary: it sees the write no matter who made it.

## Why This Works

Registry Run keys are the default persistence mechanism on Windows for the same reasons scheduled tasks are popular, minus the audit-policy friction:

1. **The OS re-launches the entry for free at every logon (Run) or once at next logon (RunOnce)** — no service to register, no file to drop in a watched folder.
2. **HKCU Run keys need no privileges** — any code running as a normal user can write its own persistence. This is why it is the go-to for the initial, pre-escalation foothold.
3. **It hides in a crowd** — a typical workstation has dozens of legitimate Run entries, so a single extra one is easy to overlook by eye.

The structural weakness the defender exploits: **the persistence only works if the value is physically written to the registry**, and Sysmon EID 13 observes that write directly. Unlike the process-creation view (which an attacker can dodge by avoiding `reg.exe` and using an API), the *outcome* — a new value under a Run key — is unavoidable. Any mechanism that achieves Run-key persistence must produce an EID 13 event on a monitored key. That makes the EID 13 search a true tripwire.

The detection follows the same "low-friction tripwire" pattern as T1053.005: surface every Run-key write, decorate with risk-indicator fields, and let the analyst sort the noisy ones to the top.

## Tuning Notes

Validated end-to-end on 2026-06-03 against Atomic Red Team `T1547.001-1` ("Reg Key Run", HKCU) and `T1547.001-2` ("Reg Key RunOnceEx", HKLM). Both fired the primary EID 13 search cleanly. Pre-flight sanity check (`index=endpoint EventCode=13 | stats count`) returned 239 over the window — EID 13 was confirmed flowing before any SPL iteration, applying the "verify the data is really in the index first" lesson. Findings below.

**Iteration loop #1 — `match()` returns a boolean, not a number.** The first-draft `no_extension` field used `if(match(Details, "...")=0, "yes", "no")`. Splunk rejected the whole search with `Error in 'EvalCommand': Type checking failed. The '==' operator received different types.` — `match()` evaluates to a boolean (`true`/`false`), and comparing a boolean to the integer `0` with `=` is a type error. **Fix:** invert the conditional instead of comparing to zero — `if(match(Details, "..."), "no", "yes")`. This applies to every flag field built on `match()`; the discovery detections (T1087, T1082) reuse the same pattern, so the corrected idiom carries forward.

**Iteration loop #2 — RunOnceEx nests, so a single-segment `value_name` blanks out.** The HKLM RunOnceEx variant writes its target as `...\CurrentVersion\RunOnceEx\0001\Depend\1` — a DLL loaded via the RunOnceEx "Depend" dependency mechanism, not a flat `Key\Value` pair. The original extraction `\\(?<run_key>...)\\(?<value_name>[^\\]+)$` requires the value to be the single final segment with no backslashes, so it matched nothing and both `run_key` and `value_name` came back **blank** for that row (the event still *surfaced* — the `TargetObject` filter and table column showed everything — it just wasn't decorated). **Fix:** order the alternation longest-first (`RunOnceEx|...|RunOnce|Run`) so the trailing `\\` anchor lands on the right keyword, and capture `value_name` as `.+` so the nested `0001\Depend\1` tail is retained instead of dropped.

**Real false positives captured — OneDrive RunOnce cleanup.** The same time window surfaced three legitimate **OneDrive** writes (`Image=...\OneDrive\Update\OneDriveSetup.exe`) creating HKCU RunOnce values named `Delete Cached Update Binary`, `Delete Cached Standalone Update Binary`, and `Uninstall <version>`, each with `Details` = `cmd.exe /q /c del|rmdir ... "C:\Users\analyst\AppData\Local\Microsoft\OneDrive\..."`. These tripped **both** `suspicious_path=yes` (the `\AppData\` target) **and** `suspicious_target=yes` (the `cmd.exe` invocation) — the worst-case flag combination — yet are entirely benign self-maintenance. This is the concrete proof that the `suspicious_*` flags are **triage hints, not alarms**: a Run-key write into AppData invoking cmd.exe is a *shape* worth a glance, not an incident. The differentiators that separate this benign case from a real threat: the writer is a Microsoft-signed updater, the values are `RunOnce` (self-deleting, not persistent `Run`), and the command is a `del`/`rmdir` cleanup, not a launcher. See the FP section for how these become an allowlist.

**Field-name confirmation.** Sysmon EID 13 auto-extracts PascalCase as expected: `EventType` (`SetValue`), `TargetObject`, `Details`, `Image`, `User`, `ProcessId`, `ProcessGuid`, `RuleName`. The `Details` field holds the value *data* for a REG_SZ as a plain string (no type prefix). HKCU is rendered as `HKU\<SID>\...` (not the literal `HKCU`) — anchoring on `CurrentVersion\Run` rather than `HKCU` is what makes the filter catch it. `RuleName` carried the config's `T1060,RunKey` tag (SwiftOnSecurity pre-dates the ATT&CK renumber from T1060 to T1547.001).

**HKLM vs HKCU confirmed in practice.** Test #1's HKCU write succeeded under the normal user token; test #2's HKLM RunOnceEx write required the elevated (High-integrity) ART session. The `hive` field correctly classified both (`HKCU (per-user)` / `HKLM (all users)`), validating the all-users-needs-admin distinction the severity rationale rests on.

## False Positive Considerations

Run-key writes are high-volume on a real endpoint. Expected legitimate sources:

- **Application installers** writing their own autostart entry during install. `ParentImage` is typically `msiexec.exe`, `setup.exe`, or a vendor installer; the target points into `Program Files`.
- **Auto-updaters and sync clients** that re-assert their Run entry — OneDrive, Dropbox, Google Drive, Teams, Steam, Discord, GPU control panels (NVIDIA/AMD), audio utilities (Realtek). These are steady background writers and the bulk of HKCU Run noise. **Observed in this lab (2026-06-03):** `OneDriveSetup.exe` wrote three HKCU **RunOnce** values — `Delete Cached Update Binary`, `Delete Cached Standalone Update Binary`, and `Uninstall <version>` — each pointing at `cmd.exe /q /c del|rmdir "...\AppData\Local\Microsoft\OneDrive\..."`. These tripped **both** `suspicious_path` and `suspicious_target`, the worst-case flag combination, while being completely benign. They are the canonical "looks bad, is fine" case this detection has to tolerate without crying wolf.
- **Microsoft's own components** — SecurityHealth, OneDrive, and similar live under HKLM Run by default.
- **Enterprise management agents** pushing autostart entries for agents and helpers.

**Tuning recommendations:**

1. **Baseline first, don't pre-whitelist.** Run the primary SPL over a 7-day window, group by `value_name` and the directory portion of `Details`. Recurring legitimate writers surface fast and become an allowlist.
2. **Triage on `suspicious_path` + `suspicious_target` first.** A Run entry pointing into `\AppData\` or `\Temp\`, or invoking a LOLBin, is the priority queue. Legitimate software almost never autostarts from a user-temp directory.
3. **Weight HKLM writes higher.** An HKLM Run write requires admin and persists for every account on the box — rarer and higher-impact than an HKCU write.
4. **Pivot on the value data path.** Once a suspicious `Details` path is found, pivot to Sysmon EID 1/11 for that path to see when the file was created and what ran it — the EID 13 event is the alert, the file/process events are the investigation.
5. **Separate `RunOnce` from `Run` when allowlisting updaters.** As the OneDrive case showed, well-behaved software often uses `RunOnce` for self-deleting maintenance (cleanup, post-update uninstall) — these fire once and remove themselves, which is the *opposite* of attacker behavior (persistent re-launch via `Run`). An allowlist keyed on `Image` = a Microsoft-/vendor-signed updater + `run_key` = `RunOnce` clears the bulk of this noise without blinding the detection to persistent `Run` writes.

### Analyst notes on this representative event

- **`RuleName: T1060,RunKey`** — this is the tag from the SwiftOnSecurity Sysmon config's Run-key rule (the config pre-dates the ATT&CK renumber, so it still uses the old T1060 ID for what is now T1547.001). Its presence confirms the write hit a monitored key; it's also a free pivot — searching `RuleName="T1060,RunKey"` returns every Run-key write the config caught.
- **`TargetObject: HKU\S-1-5-21-...\SOFTWARE\Microsoft\Windows\CurrentVersion\Run\Atomic Red Team`** — note Sysmon renders **HKCU as `HKU\<SID>`**, not the literal `HKCU`. Any detection that anchors on the literal string `HKCU` would miss this entirely; anchor on `CurrentVersion\Run` (which the SPL does). The trailing segment `Atomic Red Team` is the attacker-controlled **value name** — in real malware this is where you see the blend-in names ("Windows Defender", "MicrosoftEdgeUpdate") or random strings.
- **`Details: C:\Path\AtomicRedTeam.exe`** — the value *data*, i.e. the command that runs at next logon. This is the highest-signal field. ART's benign default is a literal `C:\Path\...` that doesn't exist; in a real intrusion this would be the actual loader path, often under `\AppData\` or `\Temp\` (which would trip `suspicious_path=yes`) or a `powershell -enc <blob>` one-liner (which would trip `suspicious_target=yes`).
- **`Image: C:\Windows\system32\reg.exe`** — the writing process (note Sysmon reported `system32` lowercase, as the process resolved it). For this ART test it's `reg.exe`, so the secondary SPL also fires and gives the parent process. If the same persistence were written by `powershell.exe` via `Set-ItemProperty`, this `Image` would read `powershell.exe` and the secondary SPL would return nothing — the EID 13 primary would still catch it. That contrast is the whole argument for making EID 13 the primary.
- **`User: DESKTOP-0DU4BT6\analyst`** with an **HKCU** target — a normal user writing their own per-user persistence. No elevation needed. This is the textbook pre-escalation foothold shape; an HKLM target from the same user would instead require (and imply) admin rights.
