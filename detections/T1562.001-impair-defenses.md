# Detection: Impair Defenses — Disable or Modify Tools

> **Status: validated 2026-06-10.** Both searches fired end-to-end against hand-run Defender-disable commands on soc-victim, in the same Defender-off session that validated [T1003.002](T1003.002-sam-credential-access.md) (SAM dumping) — because disabling Defender to *enable* the SAM dump **is** this technique. The **primary** (EID 1) classified the two process-spawning methods (`sc.exe stop WinDefend`, `reg add …DisableAntiSpyware`) and — as predicted — returned **nothing** for the three `Set-MpPreference`/`Add-MpPreference` cmdlets, which run in-session and spawn no process (the process-attribution blind spot, proven live again). The **corroborator** (EID 13) then caught what the process layer missed, including a headline finding: `Set-MpPreference -DisableRealtimeMonitoring $true` writes its registry value via **`MsMpEng.exe` as `SYSTEM`** (Defender's own service brokers the change), not via the issuing `powershell.exe` — the same actor-requests/service-performs handoff as [T1547.001](T1547.001-registry-run-keys.md) and [T1053.005](T1053.005-scheduled-task.md). The Sample Event below is a real captured EID 13. See Tuning Notes for the full findings.
>
> **Note on tooling (2026-06-10):** the current Atomic Red Team catalog has **removed the entire T1562 technique family** — `atomics/` jumps straight from `T1560.x` to `T1563.002`; there is no `T1561`, no `T1562`, and no `T1562.001` directory (confirmed via the GitHub API). As there, the detection is validated with **hand-run equivalent native commands** — which here is *not* a workaround but the natural path: the Defender-disable steps are a mandatory prerequisite for the SAM-dump validation anyway (real-time protection blocks `reg save HKLM\sam`), so we run them knowingly and capture the telemetry they generate.

## MITRE ATT&CK

- **Tactic:** Defense Evasion (TA0005)
- **Technique:** T1562 — Impair Defenses
- **Sub-technique:** T1562.001 — Disable or Modify Tools

This write-up covers the **Windows Defender** facet of the sub-technique (disabling real-time protection, disabling the AV engine via policy, adding exclusions, stopping the service, removing signatures). The broader sub-technique also covers tampering with EDR drivers, the host firewall, and event logging — the last of which overlaps [T1070.001](T1070.001-clear-event-logs.md) (clearing logs is its own sub-technique, T1070.001, but "disable logging" lives here).

## Severity

**High.** Disabling the endpoint's own defenses is almost never benign on a running production host. Legitimate causes exist (an admin troubleshooting a false positive, a managed AV migration, an installer that toggles RTP during setup) but they are rare, attributable, and tied to known maintenance windows. An adversary disables Defender for one reason: to run something Defender would otherwise block — so this technique sits *immediately before* the payload in the kill chain. It is a high-confidence "something is about to happen" signal. In this lab it is literally the prerequisite step for the [T1003.002](T1003.002-sam-credential-access.md) credential dump: the attacker blinds the defender, then steals the hashes.

## Detection Logic

Defender tampering shows up in two complementary places:

| Signal | Channel / EID | Fires when | Catches |
|---|---|---|---|
| **Tamper *command*** | Sysmon **EID 1** | A Defender-disabling binary/cmdlet runs (`Set-MpPreference`, `reg add …Defender…`, `sc stop WinDefend`, `MpCmdRun -RemoveDefinitions`) | The intent + **process attribution** (who/what/parent) — the most *complete* signal here |
| **Tamper *effect*** | Sysmon **EID 13** | A monitored Defender registry value is written (`DisableAntiSpyware`, `DisableRealtimeMonitoring`, policy `Exclusions\…`) | The state change itself, **tool-agnostic** — but only for the subset of Defender keys the Sysmon config watches |

This is the [§11 effect-tripwire-vs-attribution](../notes/splunk-spl-cheatsheet.md) pattern again — but with the roles **reversed** from T1070.001 and T1547.001. There, the service-written effect event (1102/104, EID 13) was the *universal* signal and the process event was the partial supplement. Here it is the other way around:

- **The process event (EID 1) is the more complete signal**, because several real tamper methods (ASR-rule disable, `Set-MpPreference -ExclusionPath`) write to Defender registry keys that the SwiftOnSecurity config does **not** monitor — so they produce *no* EID 13 — yet they all show up as a `Set-MpPreference` process.
- **The registry event (EID 13) is the higher-fidelity but narrower signal**: when it fires it is near-irrefutable (a Defender protection value was set to "off"), and it is tool-agnostic (catches `reg.exe`, PowerShell, or GPO equally) — but it only covers the keys in the config (see the documented gap in Tuning Notes).

So the design makes **EID 1 the primary alert** and **EID 13 the high-fidelity corroborator**, the inverse of the log-clear detection — and that contrast is itself a teaching point about when the effect-tripwire is universal versus partial.

### Primary — Defender-tamper command (Sysmon EID 1)

```spl
index=endpoint sourcetype="WinEventLog:Microsoft-Windows-Sysmon/Operational" EventCode=1
(CommandLine="*Set-MpPreference*" OR CommandLine="*Add-MpPreference*"
 OR CommandLine="*DisableRealtimeMonitoring*" OR CommandLine="*DisableAntiSpyware*"
 OR CommandLine="*DisableBehaviorMonitoring*" OR CommandLine="*DisableIOAVProtection*"
 OR CommandLine="*DisableScriptScanning*" OR CommandLine="*AttackSurfaceReductionRules_Actions*"
 OR CommandLine="*ExclusionPath*" OR CommandLine="*ExclusionProcess*" OR CommandLine="*ExclusionExtension*"
 OR CommandLine="*MpCmdRun*" OR CommandLine="*WinDefend*" OR CommandLine="*RemoveDefinitions*")
| eval method=case(
    match(CommandLine,"(?i)Set-MpPreference") AND match(CommandLine,"(?i)-DisableRealtimeMonitoring\s+\$?(true|1)\b"), "Disable real-time monitoring (Set-MpPreference)",
    match(CommandLine,"(?i)Set-MpPreference") AND match(CommandLine,"(?i)-Disable(BehaviorMonitoring|IOAVProtection|ScriptScanning|BlockAtFirstSeen)\s+\$?(true|1)\b"), "Disable Defender protection component (Set-MpPreference)",
    match(CommandLine,"(?i)-AttackSurfaceReductionRules_Actions\s+(Disabled|AuditMode)\b"), "Disable/weaken ASR rule (Set-MpPreference)",
    match(CommandLine,"(?i)(Add|Set)-MpPreference") AND match(CommandLine,"(?i)-Exclusion(Path|Process|Extension)\b"), "Add Defender exclusion",
    match(Image,"(?i)\\\\reg\.exe$") AND match(CommandLine,"(?i)\sadd\b") AND match(CommandLine,"(?i)Windows Defender") AND match(CommandLine,"(?i)(DisableAntiSpyware|DisableAntiVirus|DisableRealtimeMonitoring)"), "Disable Defender via registry policy (reg add)",
    (match(Image,"(?i)\\\\(sc|net|net1)\.exe$") OR match(CommandLine,"(?i)\bStop-Service\b")) AND match(CommandLine,"(?i)(WinDefend|WdNisSvc|Sense|SecurityHealthService)\b"), "Stop a Defender service",
    match(Image,"(?i)\\\\MpCmdRun\.exe$") AND match(CommandLine,"(?i)-RemoveDefinitions"), "Remove Defender signatures (MpCmdRun)"
  )
| where isnotnull(method)
| eval acct=coalesce(mvindex(mvfilter(User!="NOT_TRANSLATED"),0), User)
| table _time host acct method Image ParentImage CommandLine ParentCommandLine
| sort - _time
```

### Corroborator — Defender registry state change (Sysmon EID 13, tool-agnostic)

```spl
index=endpoint sourcetype="WinEventLog:Microsoft-Windows-Sysmon/Operational" EventCode=13
(TargetObject="*\\DisableAntiSpyware" OR TargetObject="*\\DisableAntiVirus"
 OR TargetObject="*DisableRealtimeMonitoring" OR TargetObject="*\\DisableBehaviorMonitoring"
 OR TargetObject="*\\SpynetReporting" OR TargetObject="*\\SubmitSamplesConsent"
 OR TargetObject="*\\Windows Defender\\Exclusions\\*")
| eval setting=case(
    match(TargetObject,"(?i)DisableAntiSpyware$"),"Defender engine disabled (DisableAntiSpyware)",
    match(TargetObject,"(?i)DisableAntiVirus$"),"Defender AV disabled (DisableAntiVirus)",
    match(TargetObject,"(?i)DisableRealtimeMonitoring$"),"Real-time monitoring disabled",
    match(TargetObject,"(?i)DisableBehaviorMonitoring$"),"Behavior monitoring disabled",
    match(TargetObject,"(?i)SpynetReporting$"),"Cloud-delivered protection (MAPS) disabled",
    match(TargetObject,"(?i)SubmitSamplesConsent$"),"Automatic sample submission disabled",
    match(TargetObject,"(?i)\\\\Exclusions\\\\"),"Defender exclusion added (policy key)",
    1=1,"Defender setting modified"
  )
| eval value_set=if(match(Details,"(?i)0x0*1\b"),"1 (disabled / on)", if(match(Details,"(?i)0x0+\b"),"0 (re-enabled / off)", Details))
| eval acct=coalesce(mvindex(mvfilter(User!="NOT_TRANSLATED"),0), User)
| table _time host acct setting value_set Image TargetObject RuleName
| sort - _time
```

### What each piece does

**Primary (EID 1):**

- **Leading `CommandLine="*…*"` filters** are cheap index-time narrowing across every Defender-tamper verb we know; the precise classification happens in the `match()` block. ([§1](../notes/splunk-spl-cheatsheet.md) — push the coarse filter down, do the sharp work after.)
- **Binary off `Image`, arguments off `CommandLine`** — the recurring lab discipline ([§3](../notes/splunk-spl-cheatsheet.md), T1087 fix #1). `reg.exe`, `sc.exe`, `MpCmdRun.exe` are matched on `Image`; the cmdlet names and switches on `CommandLine`.
- **`-DisableRealtimeMonitoring \$?(true|1)` anchor** — note the value test. `Set-MpPreference -DisableRealtimeMonitoring $true` *disables* protection (the malicious direction); `$false` *re-enables* it (what we do in cleanup, and what a benign admin does after troubleshooting). Matching the value avoids flagging the re-enable as an attack. The `\$?` tolerates both `$true` and the bare `true`/`1` PowerShell accepts.
- **`| where isnotnull(method)` — the [T1070.001 lesson](T1070.001-clear-event-logs.md) applied verbatim.** Defender shells out to its own tooling constantly (`MpCmdRun.exe` runs on a schedule for signature updates and scans). A `*MpCmdRun*` filter with a `1=1` catch-all would flood with benign maintenance. We classify only the `-RemoveDefinitions` verb and drop everything unclassified — same "anchor on the verb, not the binary" rule ([§3](../notes/splunk-spl-cheatsheet.md), [§11](../notes/splunk-spl-cheatsheet.md)) that the `wevtutil install-manifest` FP taught us.
- **`acct` dedup** — the multivalued-`User` coalesce ([T1087 fix #2](T1087-account-discovery.md)).

**Corroborator (EID 13):**

- **Anchors on the monitored Defender value names** the SwiftOnSecurity config tags (`setup/sysmon-config.xml:723-728`): the five `Tamper-Defender` state values plus the policy `Exclusions\` subtree. When one of these is written, Defender protection state genuinely changed — there is no benign "set DisableRealtimeMonitoring to 1" on a healthy endpoint.
- **`RuleName` is tabled** because it carries the config's own ATT&CK tag — `T1089,Tamper-Defender` for the five state values (T1089 is the *old* ATT&CK ID for "Disabling Security Tools", the pre-rename of T1562.001 — the same generation gap as the `T1060,RunKey` tag in [T1547.001](T1547.001-registry-run-keys.md)) and `T1562,Tamper-Defender` for the exclusions key. Searching `RuleName="*Tamper-Defender*"` is a free pivot to every Defender-state write the config caught.
- **`value_set`** decodes the `Details` DWORD. Sysmon renders a REG_DWORD as `DWORD (0x00000001)` — **note the trailing `)`**, which is why the regex anchors with `\b` (a word boundary between the final `1` and the `)`), **not** `$`. The first draft used `0x0*1$` and silently rendered the raw `DWORD (0x00000001)` instead of the friendly label, because `$` never matched past the paren — the same "confirm the exact text against a real event" gotcha as the [T1070.001 `Domain Name:` label](T1070.001-clear-event-logs.md). The `else` branch labels `0x00000000` as the **re-enabled / off** state, so the benign cleanup write (`-DisableRealtimeMonitoring $false`) reads clearly as a re-enable rather than an attack (validated live — see Tuning Notes).

## Why This Works

The structural point is the same as the Run-key and log-clear detections: **the technique cannot achieve its goal without leaving the exact artifact we watch.** To stop Defender blocking a payload, the adversary must actually change Defender's running state — and on Windows that means either (a) invoking a Defender-management process (`Set-MpPreference`, `sc stop`, `MpCmdRun`), which Sysmon EID 1 records with full parentage, or (b) writing a Defender policy/state value, which Sysmon EID 13 records on the monitored keys. There is no "disable Defender silently and invisibly" path that avoids *both* a process and a registry write on a Sysmon-instrumented host — short of a kernel-level driver attack (EDR-killer BYOVD), which is a different, louder technique (a new unsigned/vulnerable driver load, Sysmon EID 6).

And because the Universal Forwarder ships each event off-host the instant it is written, the tamper is recorded on the Splunk indexer *before* Defender is even fully down — the same "the act of evading generates its own alarm, and it is already off-box" inversion that makes log-clearing self-defeating ([T1070.001 "Why This Works"](T1070.001-clear-event-logs.md)).

## Tuning Notes

**Validation findings (2026-06-10) — what the live run taught us:**

- **The cmdlet blind spot, proven live (again).** Of the five impair commands, only the two that **spawn a process** appeared in the primary: `sc.exe stop WinDefend` (`method=Stop a Defender service`) and `reg add …DisableAntiSpyware` (`method=Disable Defender via registry policy (reg add)`). The three `Set-MpPreference`/`Add-MpPreference` cmdlets ran **in-session** and produced **no EID 1** at all — the exact process-attribution blind spot first proven with the bare `Clear-EventLog` in [T1070.001](T1070.001-clear-event-logs.md). This is *why* the EID 13 corroborator is not optional here: the most common PowerShell-native disables are invisible to the process layer.
- **Headline finding — `Set-MpPreference` writes via `MsMpEng.exe` as `SYSTEM`, not the issuing shell.** The EID 13 for `DisableRealtimeMonitoring` was authored by `Image=C:\ProgramData\Microsoft\Windows Defender\Platform\…\MsMpEng.exe`, `User=NT AUTHORITY\SYSTEM` — **Defender's own service engine brokered the registry change**, the issuing `powershell.exe` never touched the key. This is the same actor-requests / service-performs handoff as [T1547.001](T1547.001-registry-run-keys.md)'s `schtasks→svchost` and [T1053.005](T1053.005-scheduled-task.md). **Attribution consequence:** the EID 13 alone attributes the change to `MsMpEng`/`SYSTEM` (the broker), *not* to the human `analyst` who ran the cmdlet — so for cmdlet-driven tampering you must triangulate with **PowerShell Script Block Logging (EID 4104)**, which this lab has enabled and which would carry the literal `Set-MpPreference -DisableRealtimeMonitoring $true` in the user's session. The effect-tripwire tells you *what changed*; the script/process layer tells you *who*.
- **Value-direction discrimination confirmed.** Two EID 13s landed on `DisableRealtimeMonitoring`: `DWORD (0x00000001)` at the disable (Step B) and `DWORD (0x00000000)` at the cleanup re-enable (`-DisableRealtimeMonitoring $false`). The primary's value-anchored regex (`\$?(true|1)`) correctly flags only the *disable*; the corroborator's `value_set` now labels the `0x0…0` write as **re-enabled/off** rather than as an attack. The benign re-enable is visible and clearly distinguished from the malicious disable — exactly the design intent.
- **`reg add` to the policy key fired cleanly** (`HKLM\SOFTWARE\Policies\Microsoft\Windows Defender\DisableAntiSpyware`, `Details: DWORD (0x00000001)`, `RuleName: T1089,Tamper-Defender`, `Image: reg.exe`, `User: analyst`) — both the primary (process) and the corroborator (registry) caught it, the high-confidence both-layers case.
- **`ParentImage` differs by harness.** Hand-run from an interactive PowerShell, these had `ParentImage=powershell.exe`; the ART dump tests in the same session had `ParentImage=cmd.exe` (cmd-based atomics). Neither is the "interesting" parent a real intrusion would show — operator-shell colour only.
- **`sc.exe stop WinDefend` behaviour:** the `sc.exe` process spawned and was classified, regardless of whether the service actually stopped (WinDefend is protected and the stop is typically denied) — the detection catches the **attempt**, same intent-not-outcome principle as the denied `reg export HKLM\security` in [T1003.002](T1003.002-sam-credential-access.md).

**Pre-flight calibration (the [§1 "is the data in the index" lesson](../notes/splunk-spl-cheatsheet.md)):**

- **EID 1** is the lab's workhorse — confirmed flowing in every prior detection. No concern.
- **EID 13 is the one to verify**, because — exactly as with the T1003.001 EID 10 gap — *the registry value has to be one the Sysmon config actually monitors*, or it never lands. Confirmed by config read (`setup/sysmon-config.xml:723-728`): the five `Tamper-Defender` state values and the policy `Exclusions\` key **are** monitored. So a `reg add …\Windows Defender" /v DisableAntiSpyware /d 1` write **will** produce EID 13. Run `index=endpoint EventCode=13 | stats count` for the window to confirm EID 13 is flowing generally before iterating.

**Known gap — the config monitors only a *subset* of Defender keys (document, don't pretend the corroborator is universal):**

- **`Set-MpPreference -ExclusionPath` writes to the *preference* key** `HKLM\SOFTWARE\Microsoft\Windows Defender\Exclusions\Paths\…`, **not** the *policy* key `HKLM\SOFTWARE\Policies\Microsoft\Windows Defender\Exclusions\…` that the config's line 728 watches (`begin with`). So a `Set-/Add-MpPreference` exclusion shows up in the **primary (EID 1)** but produces **no EID 13** on this config. Only a GPO-pushed (policy-key) exclusion trips the corroborator. *This is the likely reason the lab's own setup-time `Add-MpPreference -ExclusionPath C:\AtomicRedTeam` did not generate a Defender-exclusion EID 13.* A reasonable config hardening (future) is to add the preference-key `Exclusions\` subtree to the Sysmon registry rules; until then, EID 1 is the catch for preference-key exclusions.
- **ASR-rule disables write to** `HKLM\SOFTWARE\Policies\Microsoft\Windows Defender\Windows Defender Exploit Guard\ASR\Rules` — **not** monitored by this config. ASR tamper is therefore an **EID 1-only** catch here (`AttackSurfaceReductionRules_Actions Disabled`). Same hardening note.
- **`Set-MpPreference -DisableRealtimeMonitoring` is expected to hit the monitored** `…\Real-Time Protection\DisableRealtimeMonitoring` value (config line 726, `end with`) — **verify live**, because Defender's RTP key is in the tamper-protected hive and the write may be brokered in a way Sysmon observes differently (or, if Tamper Protection is still on, silently no-op'd — see the operational caveat in the Test Case).

**Tamper Protection blind spot (carried from the T1003.001 session lessons):** toggling **Tamper Protection** itself is a GUI-only action (`Set-MpPreference` cannot turn it off — it silently no-ops while TP is on). There is no clean Sysmon process/registry artifact for the TP toggle in this lab's instrumentation, so this detection does **not** claim to catch the TP-off action itself — only the protection changes that *follow* once TP is off. Note this honestly rather than implying full coverage.

## False Positive Considerations

The benign rate is low but real:

- **Admin troubleshooting a false positive.** An admin briefly disables RTP to let a wrongly-quarantined tool run. Identifiable: interactive admin session, short-lived, usually re-enabled (`-DisableRealtimeMonitoring $false`) soon after. Confirm with the human rather than silently allowlisting.
- **Software installers that toggle RTP / add an exclusion during setup.** Some legitimate dev tools, AV migrations, and backup agents add a Defender exclusion or pause RTP. `ParentImage` is an installer (`msiexec.exe`, vendor `setup.exe`); the excluded path points into the product's own install dir. Baseline the specific installer + path, allowlist that, not the technique.
- **Managed-AV / EDR migration.** When an org cuts over from Defender to a third-party AV, Defender is disabled by policy fleet-wide. This is a known change window — allowlist by window + management account, not by event.
- **Defender's own maintenance (the corroborator's analogue of the T1070.001 `wevtutil install-manifest` FP).** `MpCmdRun.exe` runs constantly for scheduled scans and signature updates, parented by `MsMpEng.exe` as SYSTEM. The primary SPL classifies **only** the `-RemoveDefinitions` verb and drops the rest (`| where isnotnull(method)`), so routine `MpCmdRun` activity does not surface — the same positive-classifier discipline as the log-clear secondary.
- **Not this technique — don't confuse:** Defender *signature updates* sometimes write benign values under the Defender key tree, but not the specific `Disable*`/policy values the corroborator anchors on. The anchored value names keep these out.

**Tuning recommendations:**

1. **Alert on the primary (EID 1); use the corroborator (EID 13) to raise confidence.** A `Set-MpPreference -DisableRealtimeMonitoring $true` (primary) corroborated by a `DisableRealtimeMonitoring` EID 13 in the same second is near-irrefutable.
2. **Weight the *disable* direction, ignore the *enable* direction.** The value-anchored regexes already do this — `$true`/`1` is the alert, `$false`/`0` (re-enable) is not.
3. **Correlate forward — this is a pre-payload signal.** When Defender is disabled, immediately pivot forward in `index=endpoint` for whatever ran next under the same session: a credential dump ([T1003.002](T1003.002-sam-credential-access.md)), a malware drop, a download-and-execute. The disable is rarely the goal; it is the door being propped open.
4. **Close the config gap if exclusion/ASR coverage matters.** Add the preference-key `Exclusions\` subtree and the `…Exploit Guard\ASR\Rules` key to the Sysmon registry rules to make the EID 13 corroborator cover those methods too.

## Test Case

ART no longer ships T1562 atomics (see the status note), so we validate by **hand-running the native Defender-disable commands** in an **elevated PowerShell** on soc-victim. These are the same disables documented as the T1003.001 prerequisite — running them here serves double duty: they generate this detection's telemetry *and* they unblock the [T1003.002](T1003.002-sam-credential-access.md) SAM dump that follows in the same session.

> **⚠️ Operational caveat — these really do disable your endpoint's AV.** Run them knowingly, capture the telemetry, then **re-enable everything in cleanup** (step list below). Per the recurring [Defender-disable lesson](T1003.001-lsass-access.md): **Tamper Protection must be turned off in the GUI first** (Windows Security → Virus & threat protection → Manage settings → Tamper Protection → Off), or every `Set-MpPreference` below silently no-ops.

```powershell
# Elevated PowerShell on soc-victim. Tamper Protection already OFF via the GUI (see caveat).

# (1) Disable real-time monitoring -> EID 1 (Set-MpPreference) + (expected) EID 13 DisableRealtimeMonitoring
Set-MpPreference -DisableRealtimeMonitoring $true

# (2) Disable Defender engine via policy registry -> EID 1 (reg.exe add) + EID 13 DisableAntiSpyware
reg add "HKLM\SOFTWARE\Policies\Microsoft\Windows Defender" /v DisableAntiSpyware /t REG_DWORD /d 1 /f

# (3) Disable the LSASS-credential-theft ASR rule -> EID 1 only (ASR key not in this Sysmon config)
Set-MpPreference -AttackSurfaceReductionRules_Ids 9e6c4e1f-7d60-472f-ba1a-a39ef669e4b2 `
                 -AttackSurfaceReductionRules_Actions Disabled

# (4) Add a Defender exclusion -> EID 1 only (preference key, not the monitored policy key)
Add-MpPreference -ExclusionPath "C:\Users\Public\Downloads"

# (5) (Optional) attempt to stop the service -> EID 1 (sc.exe). WinDefend is protected and the
#     stop will likely be DENIED while running, but the *attempt* is the telemetry we want.
sc.exe stop WinDefend
```

**Predicted signal mapping** (the validation criterion — to be confirmed live):

| Command | Primary (EID 1) `method=` | Corroborator (EID 13) `setting=` |
|---|---|---|
| (1) `Set-MpPreference -DisableRealtimeMonitoring $true` | `Disable real-time monitoring (Set-MpPreference)` | **Real-time monitoring disabled** *(expected — verify; RTP key is tamper-hive)* |
| (2) `reg add … DisableAntiSpyware /d 1` | `Disable Defender via registry policy (reg add)` | **Defender engine disabled (DisableAntiSpyware)** ✓ (policy key, monitored) |
| (3) ASR rule → Disabled | `Disable/weaken ASR rule (Set-MpPreference)` | **(none)** — ASR key not in this config (documented gap) |
| (4) `Add-MpPreference -ExclusionPath …` | `Add Defender exclusion` | **(none)** — preference key, not the monitored policy key (documented gap) |
| (5) `sc.exe stop WinDefend` | `Stop a Defender service` | **(none)** — service control, no registry write |

Commands (2) vs (3)/(4) are the teaching pair: **all four trip the primary, but only the policy-key write (2) trips the corroborator** — the live proof of why EID 1 is primary here and the EID 13 effect-tripwire is *partial* (the inverse of T1070.001, where the effect event was universal).

**To validate end-to-end:**

1. Confirm the VM clock reads Central; note wall-clock time.
2. **Step zero:** confirm EID 13 is flowing generally — `index=endpoint EventCode=13 | stats count` non-zero. (The Defender-state EID 13s appear only *after* the writes.)
3. Turn Tamper Protection **off** in the GUI (caveat above), then run commands (1)–(5) in order.
4. Run the **primary** SPL ("Last 15 minutes") — confirm five rows, one per command, each classified by `method`.
5. Run the **corroborator** SPL — confirm the **DisableAntiSpyware** row (command 2) and check whether the **DisableRealtimeMonitoring** row (command 1) appears (the open question). Confirm commands (3)/(4)/(5) produced **no** EID 13 — the documented gap, proven live.
6. **Copy one full raw EID 13 event** (the DisableAntiSpyware one) back here so the Sample Event below is replaced with the real capture and this file flips to "(validated)".
7. **Cleanup — re-arm the endpoint:**
   ```powershell
   Set-MpPreference -DisableRealtimeMonitoring $false
   reg delete "HKLM\SOFTWARE\Policies\Microsoft\Windows Defender" /v DisableAntiSpyware /f
   Set-MpPreference -AttackSurfaceReductionRules_Ids 9e6c4e1f-7d60-472f-ba1a-a39ef669e4b2 -AttackSurfaceReductionRules_Actions Enabled
   Remove-MpPreference -ExclusionPath "C:\Users\Public\Downloads"
   sc.exe start WinDefend
   ```
   Then **turn Tamper Protection back ON in the GUI.** Verify with `Get-MpPreference | Select DisableRealtimeMonitoring` → `False`.

> **Do the T1003.002 SAM dump *between* step 5 and step 7** — while Defender is down. That is the single Defender-off window that validates both detections; see [T1003.002 Test Case](T1003.002-sam-credential-access.md).

```
Image: C:\ProgramData\Microsoft\Windows Defender\Platform\4.18.26050.15-0\MsMpEng.exe
TargetObject: HKLM\SOFTWARE\Microsoft\Windows Defender\Real-Time Protection\DisableRealtimeMonitoring
Details: DWORD (0x00000001)
User: NT AUTHORITY\SYSTEM
```

### Analyst notes on this real event

- **`Image: …\MsMpEng.exe` + `User: NT AUTHORITY\SYSTEM` — the headline.** The human ran `Set-MpPreference -DisableRealtimeMonitoring $true` in an `analyst` PowerShell session, but the registry write was committed by **Defender's own engine (`MsMpEng.exe`) as `SYSTEM`**. The issuing `powershell.exe` produced no EID 1 and is nowhere in this event. So the EID 13 catches the *change* but attributes it to the *broker*, not the *actor* — to name `analyst` you correlate with PowerShell Script Block Logging (EID 4104). Same actor-requests / service-performs pattern as [T1547.001](T1547.001-registry-run-keys.md) (`schtasks→svchost`).
- **`Details: DWORD (0x00000001)`** — the `1` is the "real-time monitoring *disabled*" state. The cleanup re-enable produced a sibling EID 13 with `Details: DWORD (0x00000000)` (real-time monitoring back on) from the same `MsMpEng`/`SYSTEM` writer — proving the detection distinguishes the malicious disable from the benign re-enable.
- **`RuleName: T1089,Tamper-Defender`** — the SwiftOnSecurity config's tag for the Defender-state rule group (old ATT&CK ID T1089, the pre-rename of T1562.001 — same generation gap as the `T1060,RunKey` tag in [T1547.001](T1547.001-registry-run-keys.md)). Confirms the write hit a monitored Defender key; `RuleName="*Tamper-Defender*"` is a free pivot to every Defender-state write the config caught.

For contrast, the **policy-key** disable (`reg add … DisableAntiSpyware`) produced an EID 13 authored by **`reg.exe` as `analyst`** — because that method goes through a real process, so this one *also* fired the primary EID 1 with full parentage:

```
RuleName: T1089,Tamper-Defender
Image: C:\Windows\system32\reg.exe
TargetObject: HKLM\SOFTWARE\Policies\Microsoft\Windows Defender\DisableAntiSpyware
Details: DWORD (0x00000001)
User: DESKTOP-0DU4BT6\analyst
```

The two events side by side are the whole lesson: a `reg.exe`-authored write is attributable from the registry event alone; an `MsMpEng`-brokered `Set-MpPreference` write is not — the effect-tripwire sees both, the process layer sees only the former.
